# Сравнение, контракт ожиданий и бронь с пожеланием

Задача 6.3. Всё здесь считается кодом из структур поиска 6.1 (`WishEval`, `Variant`), без LLM. Подсказка, инструменты и формат ответов агента диалога не менялись, поэтому кеш диалога остаётся валидным (проверка — в конце).

## Шортлист

Хранится в состоянии сессии диалога (`dialog_sessions.state`, поле `shortlist`, до 10 отелей, TTL сессии — час). Сервис `booking.Service` читает и пишет состояние как JSON и не теряет чужие поля (память диалога). Реплей кеша и существующие сессии не затрагиваются: поле необязательное.

- `GET /api/sessions/{id}/shortlist` — список `{id, name}`;
- `POST /api/sessions/{id}/shortlist/{hotel_id}` — добавить (повтор не дублирует; отеля нет — 404);
- `DELETE /api/sessions/{id}/shortlist/{hotel_id}` — убрать.

Вход в сравнение (`сравни шортлист`) и в «похожий» (поле `Current` сессии и номера выдачи остаются как были).

## Сравнение

`POST /api/compare`. Либо `{session_id | wishes, hotel_ids: [2–3]}` — лучшие варианты разных отелей, либо `{session_id | wishes, hotel_id, category_ids: [2–3]}` — категории одного отеля. Желания берутся из запроса (`wishes`) или из сессии; фильтры цены и звёзд к сравнению не применяются (гость уже выбрал отели, цена остаётся в варианте).

Для каждого отеля берётся лучший вариант номера для этого гостя (как в 6.1: категория + пожелание + вероятность). Ответ идёт в порядке подачи:

1. **Вывод** (`verdict`, `winner`). Правило `domain.Compare`: меньше нарушенных must → больше выполненных желаний → выше оценка. Оценки, различающиеся меньше `CompareTieScore = 0,05`, равны (при 0,03 вывод прыгал бы от мелочей): «A и B равноценны по вашим желаниям; решает «<желание с наибольшим весом>»…», без различий — «решает цена». Лучшим при нарушении must объясняется нарушением.
2. **Нарушения жёстких желаний** (`violations`, по сторонам).
3. **Существенные различия** (`differences`): только желания гостя. Числа сравниваются по значениям с порогом `significant_diff` из реестра (ниже — «одинаково», список `same`), остальное — по оценке с тем же порогом 0,05. В каждой строке — объяснение из 6.1 с источником и уверенностью (`texts`) и короткий статус (`short`: «гарантирован», «шанс ~25 % с пожеланием», «под вопросом, ~70 % с пожеланием»).
4. **Цена компромисса** (`tradeoff`): разница цены лучшего варианта и самого дешёвого из остальных и что за неё: «+65 € за ночь (Vista mar против Standard) — вид на море: гарантирован вместо «под вопросом, ~70 % с пожеланием»». Лучший вариант, который ещё и дешевле, называется так.
5. **Неуверенное** (`uncertain`): пункты «под вопросом», «данных нет» и несовпадение с открытым конфликтом; у каждого `action: "ask_hotel"` (`POST /api/contract/ask`).
6. **«Как пройдёт ваш день»** (`days`): желания сгруппированы по `day_part` из реестра (`morning` | `day` | `night`), без него — «Прочее». Сейчас: `sea_view` — утро, `walk_to_beach`, `walk_to_metro` — день, `noise_night`, `night_services`, `night_pharmacy`, `blackout_curtains` — ночь. Поле читают только сравнение и API; в `list_characteristics` агентов оно не попадает (тесты `TestListCharacteristicsHasNoDayPart`, `TestCharacteristicsViewHasNoDayPart`), поэтому кеш агентов не меняется.

Несовпадение, которое оспаривает открытый конфликт (название «Sea View» против расчёта, гости против расчёта), в сравнении и контракте называется «под вопросом (источники спорят)», а не «не совпало»: честнее при споре источников. Ранжирование поиска это не меняет.

### Команда в чате

Фразы «сравни первый и третий», «сравни 2 и 3», «сравни Hotel Arts и Hotel Omm», «сравни шортлист» разбирает код до вызова модели (`domain.ParseCompareCommand`, `dialog.turnCompare`). Номера берутся из последней выдачи сессии, названия — по тому же сопоставлению, что у «похожего». Событие SSE `compare` (тело как у ответа `POST /api/compare`), затем `message` (вывод + цена компромисса) и `done`. Если отелей меньше двух, отель не понят или шортлист пуст — только `message` с объяснением. В шортлисте больше трёх отелей — сравниваются первые три, гостю это сказано. Остальные фразы идут прежним путём.

## Контракт ожиданий

`POST /api/contract {session_id | wishes, hotel_id, category_id, wish?}`. Пункты — желания гостя по выбранному варианту, в каждом `kind`, вероятность, уверенность, источник и открытый конфликт:

| `kind` | Что значит |
| --- | --- |
| `guaranteed` | гарантировано (у категории подходят все номера или факт отеля подтверждён) |
| `chance` | шанс N % (доля подходящих номеров) |
| `wish_pending` | с пожеланием, если отель подтвердит (шанс с пожеланием) |
| `wish_confirmed` | с пожеланием: отель гарантирует пожелания |
| `wish_refused` | с пожеланием: отель не гарантирует пожелания |
| `uncertain` | под вопросом: низкая уверенность, конфликт, устарело |
| `unknown` | неизвестно, данных нет |
| `mismatch` | не совпадёт |

`offer` — пожелание, которое предлагает система («восточная сторона, этаж 4+», фасад, вероятность). Передав `wish {facade_id, floor_from}`, гость получает контракт с пожеланием. У неуверенных и неизвестных пунктов `action: "ask_hotel"`.

### Спросить отель

`POST /api/contract/ask {session_id, hotel_id, key}`. Вопрос про характеристику отеля, а не от имени гостя: один ответ для всех. `Interviewer.AskAbout`:

1. есть живой вопрос по ключу (любая сущность, в том числе вопрос о категории «Sea View») — он переиспользуется, дубль не создаётся (`status: existing`);
2. иначе запускается обычный раунд интервьюера по отелю: ценность = спрос × неуверенность × влияние, порог и недельный бюджет 3 вопроса (правило 6.1). Вопрос создан и отправлен — `created`; создан, но ждёт бюджета или порога — `queued`; вопрос не нужен — `none`;
3. спрос по ключу записывается один раз за сессию.

Гостю отвечаем «Спросили отель…», бронь не блокируется ни в одном случае.

## Бронь

`POST /api/bookings {session_id | wishes, hotel_id, category_id, wish?{facade_id, floor_from}}`, `GET /api/bookings/{id}`. Оплаты нет, создаётся заявка (`bookings`: `session_id`, `wishes` — пожелание, `expectations` — снимок контракта, `wish_question_id`; миграция `0021`). Снимок контракта строит сервер по состоянию на момент брони, а не клиент: клиентскому снимку нельзя доверять, и он мог бы разойтись с оценкой.

Пожелание должно совпадать с предложенным системой (`offer`); для категории с гарантией пожелание не нужно и отклоняется (400).

### Вопрос `wish_guarantee`

С пожеланием отельеру уходит вопрос формата confirm «Гость бронирует «<категория>» с пожеланием «<…>»: можете гарантировать?» по характеристике `wish_guarantee`.

- **Один вопрос на отель.** Если вопрос уже открыт, новая бронь его переиспользует (`question_reused`). Копящийся вопрос отправляется сразу.
- **Вне недельного бюджета:** бронь с пожеланием — естественный момент общения (PROJECT_CONTEXT, «Общение с отельером»).
- **Если отельер уже отвечал**, вопрос не создаётся, статус известен сразу.
- Ответ «да» → свидетельство `wish_guarantee = true` → у следующих гостей вероятность выполнения пожелания `0,95`. Ответ «нет» → `false` → `0,4` (`WishRefusedProbability`); без ответа остаётся `0,7`. Ответ «нет» значим: гость с пожеланием у такого отеля видит честный низкий шанс.
- **Статус пожелания в брони:** `waiting` («ждём подтверждения отеля») → `confirmed` («отель подтвердил») или `refused` («отель не гарантирует»). Статус читается из текущего ответа отеля при каждом `GET /api/bookings/{id}`, а не копируется в бронь.
