- Демо-данные в репозиторий класть можно и желательно, но нужно описать процесс их получения.
- Базовые характеристики, которые уже есть на карточке Островка (звёзды, цена, завтрак, Wi-Fi, категории номеров и т. п.), можно замокать.
- Большие артефакты и модели в git не хранить. LLM — через OpenAI-совместимое API.
- Трек не про DS. Цель — простой путь от «хочу» до «бронь» без разочарований на месте. Геоданные — пример подхода, не рамка.
- Обязательный фундамент: система знает об отеле то, чего нет в карточке, и может сказать, откуда она это знает. LLM, которая «угадывает» факт, — не решение.
- Флоу можно переизобретать: диалог, «найди похожий», новая роль отельера, новый момент брони.

Открытые вопросы (отправлены, ждём ответа): критерии и их веса; требования к фронтенду; формат защиты и запуск экспертами; допустимость Барселоны; нужен ли типовой функционал сервисов бронирования (авторизация, избранное, настройки, рассылки); источники отзывов и фото; имитация брони без оплаты.

## 2.1 Технические правила организаторов (обязательно)

- Файлы в корне: `README.md`, `docker-compose.yml`, `Dockerfile`, `.env.example`.
- Запуск строго: `git clone` → `cp .env.example .env` → `docker compose up --build` → `http://localhost:8080`. Без ручных доустановок, без доп. аргументов, ориентир ≤ 10 минут на ноутбуке.
- Приложение в контейнере слушает 8080, проброс `8080:8080`.
- Multi-stage build, лёгкий рантайм без dev-инструментов, процесс под непривилегированным пользователем.
- `/health` → 200, `{"status":"ok"}`; healthcheck в Compose; `depends_on` с `condition: service_healthy`.
- Все зависимые сервисы (БД и т. п.) — в Docker. Миграции и сиды автоматически на старте.
- Версии базовых образов и зависимостей зафиксированы (не `latest`). При сборке на Apple Silicon — `platform: linux/amd64`.
- Логи в stdout/stderr. В рантайме контейнера только POSIX sh, без bash-специфики.
- Секреты только в `.env`; без реальных секретов в git. Без приватных зависимостей.
- Большие артефакты в git не храним; LLM через OpenAI-совместимое API.
- README по шаблону организаторов: описание, ссылка на видео, быстрый старт, ресурсы, зависимости, переменные окружения со значениями по умолчанию, сидирование, маршруты (`/`, `/health`), тестовые учётные данные (у нас — переключатель ролей).
- Желательно: Makefile (`make up/down/seed`), CI с `docker build` и линтером.

Следствие для LLM: у жюри может не быть ключа. Поэтому без `LLM_API_KEY` приложение работает в режиме кеша: демо-сценарии отвечают из сохранённых ответов, а UI показывает, что включён режим без LLM.

## 3. Концепция продукта

Агент ведёт человека от расплывчатого желания до конкретного номера и закрывает сомнения до оплаты.

1. **Диалог вместо фильтров.** Пользователь пишет своими словами. Агент задаёт 1–2 уточнения, только если от них зависит выдача.
2. **Выдача с объяснением.** На каждой карточке: что совпало, что под вопросом, откуда известно (источник, уверенность, дата).
3. **«Похожий на этот».** Поиск по профилю собранных характеристик, а не по звёздам.
4. **Контракт ожиданий.** Перед бронью — список важного для этого гостя с уверенностью по каждому пункту. Неуверенное агент сам уточняет у отельера. Ответ сохраняется в профиль отеля для всех.
5. **Бронь с пожеланием.** Гость бронирует конкретную категорию и пожелание («двор, этаж 3+»). Оплаты нет, создаётся заявка.
6. **Отельер.** Видит, что узнала система и что спрашивают гости. Подтверждает, исправляет, отвечает один раз для всех.

### Объём

## 5. Характеристики

Вычисляемые, ядро:

- **noise_night** (фасад): карта шума BCN плюс оценка по OSM (класс дорог, бары и клубы в радиусе). Два источника, есть что сверять.
- **sea_view** (фасад × этаж): лучи из точки фасада в сторону моря, пересечение с полигонами зданий, сравнение высот. Результат — минимальный этаж, с которого видно море.
- **walk_to_beach, walk_to_metro** (отель): маршрут по пешеходному графу OSM (Дейкстра), минуты.
- **night_services** (отель): что открыто ночью в радиусе, по opening_hours.
- **climate_by_month** (район): Open-Meteo.

Если останется время: sunrise_sun (рассвет над морем по месяцам), landmark_view (Саграда Фамилия), учёт рельефа в маршрутах.

Только от отельера: питомцы (виды, вес, цена); затемняющие шторы; шумоизоляция; **какие категории номеров выходят на какой фасад** (мост от фасадов к номерам); возможность гарантировать пожелание к номеру.

## 6. Модель данных (Postgres 16 + PostGIS)

Геометрия хранится в SRID 4326; для расчётов в метрах — `geography` или проекция в EPSG:25831 (ETRS89 / UTM 31N, родная для Барселоны). Значения и доказательства — `jsonb`, время — `timestamptz`.

```
-- исходные геоданные (заполняет cmd/collect, попадают в сиды)
buildings(id, osm_id, catastro_ref, geom geometry(MultiPolygon,4326),
          levels int, height_m real, height_source text)   -- catastro | osm_levels | osm_height | default
noise_segments(id, source_ref, geom geometry(LineString,4326), lden_db real, ln_db real)
pois(id, osm_id, kind, name, geom geometry(Point,4326), tags jsonb)   -- бары, аптеки, метро, пляжи, магазины
coastline / sea(id, geom)                                             -- полигон моря или береговая линия
walk_edges(id, source, target, geom geometry(LineString,4326), length_m real)

-- предметная модель
hotels(id, osm_id, name, geom geometry(Point,4326), district, building_id, card jsonb)  -- card: мок базовой карточки
facades(id, hotel_id, azimuth_deg real, geom geometry(LineString,4326), length_m real, faces_street bool)
room_categories(id, hotel_id, name, facade_ids int[])   -- facade_ids заполняет отельер

facts(
  id, entity_type text,          -- hotel | facade | facade_floor | room_category | district
  entity_id text, characteristic_key text,
  value jsonb,
  source text,                   -- osm | catastro | bcn_noise | open_meteo | computed | hotelier
  method text,                   -- имя инструмента и версия алгоритма
  confidence real,               -- 0..1
  observed_at timestamptz, valid_until timestamptz,
  evidence jsonb,                -- id объектов OSM, параметры расчёта, текст ответа отельера
  status text                    -- active | superseded | disputed
)
-- индекс: (entity_type, entity_id, characteristic_key) where status = 'active'

conflicts(id, entity_type, entity_id, characteristic_key, fact_ids int[], description, resolution, status)
hotelier_questions(id, hotel_id, characteristic_key, question, reason, status, answer_text, parsed jsonb, asked_at, answered_at)
bookings(id, hotel_id, room_category_id, wishes jsonb, expectations jsonb, created_at)
```

Где считать: пространственные выборки (здания на луче, POI в радиусе, ближайший сегмент шума) — SQL с GiST-индексами (`ST_Intersects`, `ST_DWithin`, `ST_ClosestPoint`, `ST_Project`, `ST_Azimuth`). Логика поверх выборок (сравнение высот по этажам, классификация шума, Дейкстра по графу, конфликты) — в Go.

Ориентиры уверенности: расчёт по авторитетным данным (кадастр, карта шума) — 0.8–0.9; расчёт по высотам из OSM — 0.5–0.7; ответ отельера — 0.9 (может оспариваться расчётом, тогда конфликт); значение только от LLM недопустимо.

Противоречие: два активных факта по одной сущности и характеристике расходятся сильнее порога характеристики. Тогда создаём conflict, ставим факты в disputed и либо разрешаем по приоритету источников, либо задаём вопрос отельеру.

## 7. Реестр характеристик

Файлы `registry/*.yaml`. Новая характеристика добавляется YAML-файлом или текстовым описанием: LLM переводит текст в YAML, выбирая только из существующих инструментов. Если инструмента нет — стратегия ask_hotelier.

```yaml
key: noise_night
title: Тишина ночью
description: Насколько тихо ночью со стороны каждого фасада
level: facade
value_type: enum # bool | enum | number | range | text
values: [quiet, moderate, loud]
ttl_days: 365
conflict_threshold: 1 # расхождение на 1 ступень уже конфликт
strategies:
  - tool: bcn_noise_map
    params: { period: night }
    confidence: 0.85
  - tool: osm_noise_estimate
    params: { radius_m: 150 }
    confidence: 0.6
ask_hotelier: "Есть ли в номерах со стороны улицы шумоизоляция или окна во двор?"
```

## 8. Стек и структура репозитория

- Бэкенд: Go, net/http или chi, JSON API; `paulmach/orb` для геометрии в Go.
- БД: **Postgres 16 + PostGIS**, образ с зафиксированной версией (например `postgis/postgis:16-3.4`), драйвер `jackc/pgx/v5`. Схема — SQL-миграции в `migrations/`, применяются приложением на старте. Демо-данные — `data/demo/seed.sql.gz`, загружаются автоматически при первом старте (initdb или командой приложения). Доступ к БД изолирован в `internal/store`.
- Импорт сырых геоданных (только у разработчика, не в рантайме): Overpass → Go, при необходимости `ogr2ogr` для кадастра (GML) и карты шума (Shapefile/GeoJSON). Результат экспортируется в seed.
- LLM: OpenAI-совместимый клиент. В `.env`: `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`. Без ключа — режим кеша.
- Фронтенд: React + Vite + TypeScript в `frontend/`, `react-leaflet` для карты, Tailwind. Ответы чата стримятся через SSE. Собранная статика встраивается в Go-бинарник через `embed`; в разработке Vite с прокси на Go. API под префиксом `/api`.
- Docker: multi-stage — node (сборка фронта) → golang (сборка бинарника) → минимальный рантайм (distroless или alpine), non-root, порт 8080.
- Запуск: `docker compose up --build`; в разработке `cd backend && go run ./cmd/server` и `cd frontend && npm run dev`.

Clean Architecture (прагматично, на 5 дней):

- Зависимости только внутрь: `adapter` → `usecase` → `domain`. `domain` не импортирует ничего, кроме стандартной библиотеки и `orb`.
- Порты объявляются в `usecase` рядом с потребителем, реализуются в `adapter`. Интерфейс заводим только там, где есть внешняя граница (БД, источники, LLM), а не для каждого типа.
- Пространственные выборки PostGIS живут в `adapter/repository/postgres` за портами вида `BuildingsAlongRay`, `PoisWithin`. Чистая логика расчёта (этажи, классификация шума, Дейкстра, конфликты) — в `usecase` и `domain`, покрывается тестами без БД.
- DTO HTTP не совпадают с сущностями домена; маппинг в `adapter/http`.

Feature-Sliced Design:

- Слои импортируют только нижележащие: `app` → `pages` → `widgets` → `features` → `entities` → `shared`. Слайсы одного слоя друг друга не импортируют.
- У каждого слайса публичный API через `index.ts`; импорт извне только через него.
- Сегменты внутри слайса: `ui`, `model`, `api`, `lib` — только нужные.
- Проверка границ: линтер `steiger` (официальный для FSD), если настройка займёт не больше 15 минут; иначе — правило в ревью.

Важно: `go:embed` не видит файлы вне Go-модуля, поэтому сборка фронтенда копируется в `backend/internal/adapter/http/dist` на этапе Docker-сборки. В разработке фронтенд запускается через Vite (`frontend/`) с прокси `/api` на Go-сервер, а встроенная статика не нужна.
