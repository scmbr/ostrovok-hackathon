## 3. Концепция продукта

Агент ведёт человека от расплывчатого желания до конкретного номера и закрывает сомнения до оплаты.

1. **Диалог вместо фильтров.** Пользователь пишет своими словами. Агент задаёт 1–2 уточнения, только если от них зависит выдача.
2. **Выдача с объяснением.** На каждой карточке: что совпало, что под вопросом, откуда известно (источник, уверенность, дата).
3. **«Похожий на этот».** Поиск по профилю собранных характеристик, а не по звёздам.
4. **Контракт ожиданий.** Перед бронью — список важного для этого гостя с уверенностью по каждому пункту. Неуверенное агент сам уточняет у отельера. Ответ сохраняется в профиль отеля для всех.
5. **Бронь с пожеланием.** Гость бронирует конкретную категорию и пожелание («двор, этаж 3+»). Оплаты нет, создаётся заявка.
6. **Отельер.** Видит, что узнала система и что спрашивают гости. Подтверждает, исправляет, отвечает один раз для всех.

## 5. Характеристики

Вычисляемые, ядро:

- **noise_night** (фасад): карта шума BCN плюс оценка по OSM (класс дорог, бары и клубы в радиусе). Два источника, есть что сверять.
- **sea_view** (фасад × этаж): лучи из точки фасада в сторону моря, пересечение с полигонами зданий, сравнение высот. Результат — минимальный этаж, с которого видно море.
- **walk_to_beach, walk_to_metro** (отель): маршрут по пешеходному графу OSM (Дейкстра), минуты.
- **night_services** (отель): что открыто ночью в радиусе, по opening_hours.
- **climate_by_month** (район): Open-Meteo.

Если останется время: sunrise_sun (рассвет над морем по месяцам), landmark_view (Саграда Фамилия), учёт рельефа в маршрутах.

Только от отельера: питомцы (виды, вес, цена); затемняющие шторы; шумоизоляция; **какие категории номеров выходят на какой фасад** (мост от фасадов к номерам); возможность гарантировать пожелание к номеру.

## 6. Модель данных (Postgres 16 + PostGIS)

Геометрия хранится в SRID 4326; для расчётов в метрах — `geography` или проекция в EPSG:25831 (ETRS89 / UTM 31N, родная для Барселоны). Значения и доказательства — `jsonb`, время — `timestamptz`.

```
-- исходные геоданные (заполняет cmd/collect, попадают в сиды)
buildings(id, osm_id, catastro_ref, geom geometry(MultiPolygon,4326),
          levels int, height_m real, height_source text)   -- catastro | osm_levels | osm_height | default
noise_segments(id, source_ref, geom geometry(LineString,4326), lden_db real, ln_db real)
pois(id, osm_id, kind, name, geom geometry(Point,4326), tags jsonb)   -- бары, аптеки, метро, пляжи, магазины
coastline / sea(id, geom)                                             -- полигон моря или береговая линия
walk_edges(id, source, target, geom geometry(LineString,4326), length_m real)

-- предметная модель
hotels(id, osm_id, name, geom geometry(Point,4326), district, building_id, card jsonb)  -- card: мок базовой карточки
facades(id, hotel_id, azimuth_deg real, geom geometry(LineString,4326), length_m real, faces_street bool)
room_categories(id, hotel_id, name, facade_ids int[])   -- facade_ids заполняет отельер

facts(
  id, entity_type text,          -- hotel | facade | facade_floor | room_category | district
  entity_id text, characteristic_key text,
  value jsonb,
  source text,                   -- osm | catastro | bcn_noise | open_meteo | computed | hotelier
  method text,                   -- имя инструмента и версия алгоритма
  confidence real,               -- 0..1
  observed_at timestamptz, valid_until timestamptz,
  evidence jsonb,                -- id объектов OSM, параметры расчёта, текст ответа отельера
  status text                    -- active | superseded | disputed
)
-- индекс: (entity_type, entity_id, characteristic_key) where status = 'active'

conflicts(id, entity_type, entity_id, characteristic_key, fact_ids int[], description, resolution, status)
hotelier_questions(id, hotel_id, characteristic_key, question, reason, status, answer_text, parsed jsonb, asked_at, answered_at)
bookings(id, hotel_id, room_category_id, wishes jsonb, expectations jsonb, created_at)
```

Где считать: пространственные выборки (здания на луче, POI в радиусе, ближайший сегмент шума) — SQL с GiST-индексами (`ST_Intersects`, `ST_DWithin`, `ST_ClosestPoint`, `ST_Project`, `ST_Azimuth`). Логика поверх выборок (сравнение высот по этажам, классификация шума, Дейкстра по графу, конфликты) — в Go.

Ориентиры уверенности: расчёт по авторитетным данным (кадастр, карта шума) — 0.8–0.9; расчёт по высотам из OSM — 0.5–0.7; ответ отельера — 0.9 (может оспариваться расчётом, тогда конфликт); значение только от LLM недопустимо.

Противоречие: два активных факта по одной сущности и характеристике расходятся сильнее порога характеристики. Тогда создаём conflict, ставим факты в disputed и либо разрешаем по приоритету источников, либо задаём вопрос отельеру.

## Источники и логика определения правды

Три семейства источников, ошибающихся по-разному. Ценность — в независимости, а не в количестве.

| Семейство | Сильная сторона | Типичная ошибка |
|---|---|---|
| Открытые данные и расчёт | беспристрастен, полное покрытие | устаревает; не видит деревьев, ремонта, новых зданий |
| Отельер | знает свой отель лучше всех | приукрашивает в свою пользу |
| Гости (анкеты после проживания) | видели сами | шумные, субъективные, их мало |

Общий принцип: **спрашивать того, кого дешевле спросить, и только когда ответ что-то меняет** — сначала расчёт, потом отельер, потом гость.

### Модель: свидетельства и байесовское сложение

- Каждое утверждение — **свидетельство** (evidence): сущность, характеристика, утверждаемое значение, источник, конкретный автор (id отельера или гостя), время, детали (параметры расчёта, текст ответа, номер и этаж гостя).
- Надёжность свидетельства `r ∈ (0,1)`:
  `r = база_источника (реестр) × поправка_репутации_автора × поправка_асимметрии × поправка_свежести`, с ограничением `[0.05, 0.97]`.
  - база: расчёт по кадастру/карте шума 0.85, расчёт по OSM 0.6, отельер 0.8, гость 0.7 — начальные экспертные значения, калибруются на этапе метрик;
  - **асимметрия:** утверждение отельера в пользу отеля (вид есть, тихо, питомцы можно) — множитель ~0.75; признание недостатка — 1.0;
  - **свежесть:** вес падает к концу `valid_until`; после — свидетельство устаревшее, характеристика ставится на пересчёт.
- Для bool/enum: стартуем с логарифма шансов 0 (50/50); каждое свидетельство добавляет `±log(r/(1−r))` к своему значению. Итог → вероятность = `confidence` факта, значение — с наибольшей вероятностью.
- **Зависимые источники считаются один раз:** в реестре у стратегии есть `independence_group`; из одной группы берётся сильнейшее свидетельство (например, два набора карты шума BCN — одна модель 2017 года).
- **Конфликт** — сильные свидетельства с обеих сторон (сумма вклада «за» и «против» выше порога). Не усредняем: создаём conflict и задаём вопрос тому, чей ответ дешевле и информативнее.
- **Разная детализация не спорит:** ответы гостей привязаны к категории номера и этажу из брони; «с 2-го этажа моря не видно» не противоречит «видно с 4-го».
- **Числа не голосуют:** минуты, дБ, расстояния — значение берётся из расчёта; ответы людей служат проверкой и триггером пересчёта.
- Вклад каждого свидетельства хранится и показывается: «уверенность 0.87: кадастр +, отельер +, 2 гостя −».
- Реализация — в `domain` (чистая функция, тесты на разобранные примеры). Формула и пример — в README.

### Репутация авторов (отельеры и гости)

- `trust = (совпадения + 1) / (всего + 2)` — по ответам на то, что известно с уверенностью > 0.9 и не исходит от самого автора. Новичок стартует с 0.5.
- **Гости:** контрольный вопрос с известным ответом в каждой анкете; признаки небрежности — все ответы одинаковые, анкета за пару секунд, противоречия внутри анкеты. Последствия: ниже вес, реже приглашения, меньше баллов.
- **Ловушка:** несогласие с расчётом ≠ мухлёж. Наказываем только за контрольные вопросы и небрежность. Несколько надёжных гостей независимо против расчёта — сигнал, что мир изменился (новое здание, ремонт): характеристика ставится на пересчёт (задача актуализации из трека).
- **Отельеры:** доля утверждений, подтверждённых расчётом и гостями; нарушенное пожелание из брони снижает доверие. От репутации зависит уверенность в непроверяемом расчётом (питомцы, шторы, шумоизоляция).

## Общение с отельером

- **Вопрос — про характеристику отеля, а не от имени гостя:** один ответ для всех будущих гостей.
- **Ценность вопроса** = спрос (сколько гостей искали или включали в контракт) × неуверенность (нет данных, низкая уверенность, конфликт) × влияние (изменит ли ответ выдачу). Ниже порога — не отправляется, копится.
- **Бюджет:** не больше N (3–5) вопросов на отель в неделю; приходят дайджестом в кабинете, отсортированные по ценности.
- **Дешёвый формат:** по возможности подтверждение «по расчёту море видно с восточной стороны с 4-го этажа — верно? да / нет / уточнить». Свободный текст — где без него нельзя; агент раскладывает его по полям.
- **Конкретные вопросы:** «из каких категорий, на какую сторону, с какого этажа», а не «есть ли вид».
- **Естественные моменты:** анкета при подключении (предзаполнена расчётом); подтверждение брони с пожеланием; повторная проверка только по сроку годности или конфликту.
- **Мотивация:** кабинет показывает упущенный спрос: «14 гостей искали тихий номер; у вас не указано, какие номера во двор».
- **Для гостя:** если ответа нет, честно «спросили отель», выдача не блокируется.
- **Демо:** имитированные отельеры-персоны — честный, ленивый (коротко и неполно), приукрашивающий. Показываем, как приукрашивающий ловится на конфликте с расчётом и теряет доверие.

## Гости: анкеты «Гуру» и профиль

- **Анкета после проживания** (имитация): только после подтверждённой брони; 1–3 вопроса строго по контракту ожиданий этого гостя; баллы «Гуру» за честность, одинаковые для «да» и «нет»; один контрольный вопрос.
- **Демо:** гости-персоны — честный, ленивый (на всё «да»), сообщающий о закрытом виде. Ленивому снижается вес, третий запускает пересчёт.
- **Профиль предпочтений:** что важно гостю (тишина, море, питомец…), из диалога, анкет и прошлых поисков; задаёт веса в поиске и сравнении. Открытый: «я помню, что вам важна тишина — верно?»; экран «что система о вас знает» с «исправить» и «забыть».
- **Данные:** согласие, минимизация, право удалить. Особые категории (здоровье, доступная среда, религиозные ограничения) — только в рамках текущего поиска, в профиль без явного согласия не сохраняем.

## Умное сравнение

- Сравниваются **лучшие варианты для этого гостя:** сначала для каждого отеля выбирается подходящий номер (категория + фасад + этаж), затем сравниваются варианты.
- Порядок: вывод («для вас лучше A, потому что…») → нарушения жёстких пожеланий → существенные различия → цена компромисса («+20 € за ночь — вид на море и тихая ночь») → неуверенное с кнопкой «уточнить у отеля».
- **Порог значимости:** в реестре у характеристики `significant_diff` (например, 5 минут, 1 ступень шума); различия ниже порога — «одинаково».
- Показываются только характеристики, важные этому гостю.
- Подача «как пройдёт ваш день»: утро (рассвет), день (пляж, метро), ночь (шум, что открыто).
- Карта рядом: отели, пешие маршруты, стрелки фасадов с видом.
- То же сравнение — для номеров внутри одного отеля.

## Спрос на характеристики

- Желания гостя, не сопоставленные с реестром, пишутся в журнал (`unmet_wishes`). Повторяющиеся — агент предлагает новую характеристику и стратегию получения (расчёт из имеющихся инструментов, отельер или анкета гостя).
- Фильтры для реестра: влияет на выбор или разочарование; различается между отелями; нет в карточке; получаемо с понятной уверенностью.
- Субъективное (вежливость персонала и т. п.) — не факт, а «мнение гостей, N ответов»; хранится и показывается отдельно от проверяемых фактов.

## Вне объёма прототипа (для питча как развитие)

Извлечение фактов из отзывов Островка (источник `guest_reviews`); полноценная ML-рекомендательная система; `pgvector` для поиска по отзывам и большого реестра; второй регион — только если останется время на этапе метрик.

## 8. Стек и структура репозитория

- Бэкенд: Go, net/http или chi, JSON API; `paulmach/orb` для геометрии в Go.
- БД: **Postgres 16 + PostGIS**, образ с зафиксированной версией (например `postgis/postgis:16-3.4`), драйвер `jackc/pgx/v5`. Схема — SQL-миграции в `migrations/`, применяются приложением на старте. Демо-данные — `data/demo/seed.sql.gz`, загружаются автоматически при первом старте (initdb или командой приложения). Доступ к БД изолирован в `internal/store`.
- Импорт сырых геоданных (только у разработчика, не в рантайме): Overpass → Go, при необходимости `ogr2ogr` для кадастра (GML) и карты шума (Shapefile/GeoJSON). Результат экспортируется в seed.
- LLM: OpenAI-совместимый клиент. В `.env`: `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`. Без ключа — режим кеша.
- Фронтенд: React + Vite + TypeScript в `frontend/`, `react-leaflet` для карты, Tailwind. Ответы чата стримятся через SSE. Собранная статика встраивается в Go-бинарник через `embed`; в разработке Vite с прокси на Go. API под префиксом `/api`.
- Docker: multi-stage — node (сборка фронта) → golang (сборка бинарника) → минимальный рантайм (distroless или alpine), non-root, порт 8080.
- Запуск: `docker compose up --build`; в разработке `cd backend && go run ./cmd/server` и `cd frontend && npm run dev`.

Clean Architecture (прагматично, на 5 дней):

- Зависимости только внутрь: `adapter` → `usecase` → `domain`. `domain` не импортирует ничего, кроме стандартной библиотеки и `orb`.
- Порты объявляются в `usecase` рядом с потребителем, реализуются в `adapter`. Интерфейс заводим только там, где есть внешняя граница (БД, источники, LLM), а не для каждого типа.
- Пространственные выборки PostGIS живут в `adapter/repository/postgres` за портами вида `BuildingsAlongRay`, `PoisWithin`. Чистая логика расчёта (этажи, классификация шума, Дейкстра, конфликты) — в `usecase` и `domain`, покрывается тестами без БД.
- DTO HTTP не совпадают с сущностями домена; маппинг в `adapter/http`.

Feature-Sliced Design:

- Слои импортируют только нижележащие: `app` → `pages` → `widgets` → `features` → `entities` → `shared`. Слайсы одного слоя друг друга не импортируют.
- У каждого слайса публичный API через `index.ts`; импорт извне только через него.
- Сегменты внутри слайса: `ui`, `model`, `api`, `lib` — только нужные.
- Проверка границ: линтер `steiger` (официальный для FSD), если настройка займёт не больше 15 минут; иначе — правило в ревью.

Важно: `go:embed` не видит файлы вне Go-модуля, поэтому сборка фронтенда копируется в `backend/internal/adapter/http/dist` на этапе Docker-сборки. В разработке фронтенд запускается через Vite (`frontend/`) с прокси `/api` на Go-сервер, а встроенная статика не нужна.
