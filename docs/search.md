# Поиск: лучший вариант номера, оценка и объяснение

Реализация — `backend/internal/domain/search.go` (формулы, тесты в `search_test.go`), сервис — `backend/internal/usecase/search`, HTTP — `backend/internal/adapter/http/search.go`. Разбор текста гостя в запрос и SSE — задача 6.2; здесь вход — структурный запрос.

## Запрос

```json
{
  "wishes": [
    {"key": "sea_view",      "importance": "must"},
    {"key": "walk_to_beach", "op": "le", "value": 10, "importance": "prefer"},
    {"key": "noise_night",   "value": "quiet", "min_floor": 3}
  ],
  "filters": {"price_max": 150, "stars_min": 3},
  "session_id": "s-42",
  "limit": 10
}
```

- `importance`: `must` (по умолчанию `prefer`). `min_floor` — номер не ниже этого этажа, только для характеристик фасада.
- `filters` — базовые фильтры мок-карточки: цена **варианта номера** за ночь и звёзды отеля. Это жёсткие условия: отель без подходящего варианта в выдачу не попадает.
- Схема желания выводится из реестра (`NormalizeWish`), характеристики в коде не перечислены:

| Характеристика в реестре | `value` | `op` по умолчанию |
|---|---|---|
| уровень отеля, `bool` | `true` / `false` (по умолчанию `true`) | `eq` |
| уровень отеля, `enum` без порядка | значение из `values` | `eq` |
| уровень отеля, `enum` упорядоченный | значение из `values`; ищется «не хуже» | в сторону выгодных значений (`favorable_values`): `le` или `ge` |
| уровень отеля, `number` | число | `le` |
| фасад с блоком `category` (`sea_view`, `noise_night`…) | значение из `category.values` (по умолчанию `category.target`) | только `eq` |

Район (`climate_by_month`), неизвестные ключи и значения вне шкалы дают ошибку 400. Новая характеристика реестра (YAML или текстом) ищется сразу, как только у неё есть факты.

## Вероятность и оценка желания

Для желания в конкретном варианте номера (категории):

- **Характеристика отеля** (`walk_to_beach`, `pets_allowed`, `night_services`…): значение берётся из факта отеля; `p = 1`, если оно подходит, иначе `0`.
- **Характеристика фасада** (`sea_view`, `noise_night`): `p_base` — доля номеров категории с нужным значением (`AssessCategory` по размещению отельера и фактам фасадов; при `min_floor` номера ниже этажа не подходят).
- **Название категории вероятности не повышает.** «Sea View» — утверждение отеля; его проверяет расчёт по фасадам и этажам. Если расчёт против, `p = 0`, а в объяснении виден конфликт «название — расчёт» (отели 57, 326, 143 в мок-данных).
- **Итог движка правды по категории против расчёта** (гости сообщили, что вид закрыт; отель 156): если итоговый факт категории не совпадает с желанием, а расчёт по размещению даёт преобладание этого значения, `p_base` умножается на `1 − уверенность`; гарантии нет, статус «под вопросом», в объяснении конфликт.

Оценка желания: `s = c·p + (1 − c)·0,5`, где `c` — уверенность факта (для `bool` и `enum` это вероятность значения, для чисел — надёжность расчёта), `p` — вероятность выполнения. Когда уверенности нет (`c = 0`), оценка 0,5 — «не знаем».

**Неизвестное не равно «нет».** Если факта нет совсем, оценка `0,4` (нейтральные 0,5 минус небольшой штраф), статус `unknown`, пометка «спросим отель». Отель из выдачи не исключается и must не нарушает.

### Правка A. Пожелание в брони

У варианта номера две вероятности:

- `p_base` — доля подходящих номеров категории («Стандарт»: 30 %);
- `p_wish` — с лучшим пожеланием «сторона, этаж N+»: **охват × вероятность, что отель выполнит**. Охват — какую часть подходящих номеров закрепляет пожелание: `min(1, номера под пожеланием / подходящие номера категории)`. Если пожелание закрепляет все подходящие номера, охват 1. Вероятность выполнения — `0,7`, пока отель пожелание не подтвердил (константа-мок `WishFulfilProbability`), и `0,95`, если отельер сообщил «можем гарантировать пожелание» (характеристика `wish_guarantee`, только от отельера: `registry/wish_guarantee.yaml`, без инструмента, с `ask_hotelier`).

> В постановке задачи `p_wish` записан как «доля номеров под пожеланием × вероятность выполнения». Доля номеров категории (30 %) уже входит в `p_base`: если умножить ещё раз, пожелание всегда было бы хуже простого шанса, а отель с 30 % в единственной категории оказывался бы нарушителем при любом пожелании. Поэтому доля берётся как охват подходящих номеров.

В оценку идёт `p = max(p_base, p_wish)`; нарушение must считается по ней же. В объяснение идут обе: `p_base`, `p_wish` и пожелание (`booking_wish`: фасад, сторона, этаж, охват, вероятность, подтверждено ли отелем). Оговорка: «гарантии нет: 30 % номеров без пожелания; с пожеланием — если отель подтвердит».

Пример: «Стандарт», 10 номеров на восточном фасаде, этажи 1–10, море видно с 8-го этажа.

| | значение |
|---|---|
| `p_base` | 3 из 10 = 0,30 |
| пожелание | «восточная сторона, этаж 8+», охват 3/3 = 1 |
| `p_wish` | 1 × 0,7 = 0,70 (с подтверждением отеля 0,95) |
| `p` | max(0,30; 0,70) = 0,70, статус «шанс», must **не нарушен** |
| без пожелания (если отель их не принимает) | `p = 0,30`, `s < 0,5`: must нарушен |

Тесты: `TestEvalCategoryWishWishAvoidsViolation`, `TestEvalCategoryWishHotelGuaranteesWishes`.

### Правка B. Числа у порога

Вокруг порога желания есть полоса `полоса = min(significant_diff, порог / 2)` (`significant_diff` — из реестра; у `walk_to_beach` и `walk_to_metro` он 2 минуты). Внутри полосы вероятность **плавная**:

`p = clamp(0,5 + (порог − значение) / (2 · полоса), 0, 1)` для «не больше» (для «не меньше» разность с обратным знаком).

На пороге `p = 0,5`, на краю полосы изнутри `p = 1`, снаружи `p = 0`. Статус: `p ≥ 0,95` — «совпало»; `0,05 ≤ p < 0,95` — «почти» (оговорка «≈ 10,5 мин, на границе»); `p < 0,05` — «не совпало» (для must это нарушение, если значение известно). Без `significant_diff` порог жёсткий (0 или 1). Полоса не шире половины порога: иначе при пороге 5 минут и `significant_diff = 5` на границе оказалось бы всё от 0 до 10 минут.

Порог 10 мин, полоса 2 (тест `TestEvalHotelWishNearThreshold`):

| значение, мин | p | статус | must |
|---|---|---|---|
| 6 | 1 | совпало | |
| 8 | 1 | совпало | |
| 9,5 | 0,625 | почти | не нарушен |
| 10 | 0,5 | почти | не нарушен |
| 10,5 | 0,375 | почти | не нарушен |
| 12 | 0 | не совпало | **нарушен** |
| 14 | 0 | не совпало | **нарушен** |

Оценка желания считается от этого `p` той же формулой `c·p + (1 − c)·0,5`, поэтому 9,5 минуты ранжируется выше 10,5.

## Статусы объяснения

| статус | когда |
|---|---|
| `match` совпало | `p ≥ 0,95` (у категории — гарантия), уверенность ≥ 0,6, нет конфликта, `weak_disagreement` и `stale` |
| `chance` шанс N % | у категории `0 < p < 1`, уверенность ≥ 0,6 |
| `uncertain` под вопросом | значение подходит, но уверенность < 0,6, открыт конфликт, факт устарел или есть слабое расхождение; а также несовпадение с низкой уверенностью |
| `near` почти | число у порога, `0,05 ≤ p < 0,95` |
| `mismatch` не совпало | значение известно, не подходит (у чисел `p < 0,05`), уверенность ≥ 0,6 |
| `unknown` | факта нет |

В структуре желания: статус, найденное значение, уверенность, `p_base` / `p_wish` / `p`, оценка, источники (`evidence`: источник, автор, надёжность, вклад, дата), `observed_at` / `valid_until` факта, конфликт, оговорка, пожелание к брони.

## Вариант номера и ранжирование

- Вариант = категория + оценки всех желаний + цена. Цена категории — мок: цена карточки × множитель по названию (Standard 1,0; Superior 1,2; Deluxe 1,45; Family 1,5; Suite 2,0; «Sea View» / «Vista mar» 1,3). В карточке цена одна на отель.
- Оценка варианта — средневзвешенное `s` по желаниям, вес `must` = 2, `prefer` = 1.
- **Лучший вариант**: меньше нарушенных must, затем выше оценка, затем дешевле.
- **Альтернатива** (одна): лучший из остальных, у которого не больше нарушений, и который **дешевле** лучшего или **даёт гарантию**, которой у лучшего нет («вид гарантирован в Делюксе за +30 € или ~25 % в Стандарте с пожеланием»).
- **Нарушение must** — `mismatch`, либо `chance`, у которого даже с пожеланием оценка ниже 0,5. Отели с нарушением остаются в выдаче, но идут **после** всех без нарушений, с пометкой (`violations`). Внутри групп — по оценке, цене, id.

## «Похожий на этот»

`GET /api/hotels/{id}/similar?limit=5&weights=sea_view:3,walk_to_beach:2`. Профиль отеля — значения его фактов по характеристикам реестра (уровень отеля; район не входит), **без звёзд и цены**. Расстояние — взвешенное среднее по характеристикам, известным хотя бы у одного из двух отелей:

- число: разница меньше `significant_diff` — 0 (одинаково), далее `min(1, |Δ| / (4·significant_diff))`;
- упорядоченный enum: `|Δ ступеней| / (ступеней − 1)`; остальные enum и bool: 0 или 1;
- вид на море (диапазон): оба без вида — 0, один без — 1, иначе `min(1, |Δ этажей| / 4)`;
- нет значения у одного из отелей — 0,5 («не знаем»).

Веса по умолчанию 1. Из запроса: `must` — 3, `prefer` — 2 (`QueryWeights`), в GET они передаются параметром `weights`. В ответе — расстояние и три главных отличия.

## Спрос

Поиск увеличивает `characteristic_demand` (`source = 'search'`) по ключам желаний. **Одна сессия поиска (`session_id`) увеличивает спрос по ключу один раз** (таблица `demand_sessions`); запрос без `session_id` считается отдельной сессией. Мок спроса (`source = 'mock'`) остаётся отдельной строкой (миграция `0019`: PK `(characteristic_key, region_id, source)`); ценность вопросов отельеру читает сумму. `collect search-demo` и тесты спрос не пишут: прогоны демо не должны двигать `value_score` и дайджест.

`make seed` сам удаляет строки `characteristic_demand` с `source = 'search'` перед дампом: в сид попадает только мок спроса.

## Ограничения

- Поиск обходит 60 отелей по одному (несколько запросов на отель, 6 параллельно). Для демо этого хватает; на тысячах отелей нужен предотбор в SQL (фильтры карточки, пространственные условия) и пакетная загрузка фактов.
- Цены категорий — мок по названию; настоящих цен категорий в данных нет.
- Для характеристики фасада желание проверяется по одному значению (`eq`); «тихо или умеренно» пока нельзя. Угловые номера не моделируются.
- `p_wish` использует константу 0,7 до подтверждения отеля; вопрос про `wish_guarantee` попадёт к отельеру обычным путём (дайджест, ценность, бюджет), спрос на него появится из поиска.
- Добавленный в реестр `wish_guarantee` виден агенту-сборщику (`list_characteristics`), поэтому записанный кеш прогонов агента на пяти отелях разойдётся с ним и пока не перезаписывается (политика: один раз в конце этапа 8). До этого в режиме кеша прогон агента по этим отелям продолжит планировщик.
