# Агент диалога

Гость пишет своими словами; агент превращает фразу в структурный запрос из `docs/search.md`, спрашивает уточнение, только когда от ответа зависит выдача, и объясняет результат без выдуманных фактов. Поиск и разбор работают без ключа LLM.

Код: `backend/internal/usecase/dialog` (ядро и агент), `backend/internal/domain/nlquery.go` (парсер), `domain/explain.go` (объяснение), `adapter/http/chat.go` (SSE), `adapter/repository/postgres/dialog.go` (сессии и `unmet_wishes`).

## Ход диалога

```
сообщение (+ choice кнопки уточнения)
  → ответ на висящее уточнение (код)
  → parse_baseline: парсер по реестру (код): желания, важность, числа, «без X», неоднозначность, непонятое
  → правило уточнения (код): спросить или продолжить с допущением
  → search / similar (search.Service из 6.1)
  → объяснение и текст выдачи строит код (по структуре WishEval); модель текст не пишет
  → сессия в Postgres, события SSE
```

Модель (если есть ключ или кеш) выбирает инструменты, текст выдачи строит код. Решать за код она не может: правило уточнения и поиск срабатывают, даже если модель их пропустила (тесты `TestAgentCannotBypassClarificationRule`, `TestAgentFallbackSearchWhenModelSkips`). Записать факт модель не может: такого инструмента нет.

### Инструменты модели

| Инструмент | Что делает |
|---|---|
| `list_characteristics` | ключи, названия и значения реестра, по которым можно искать |
| `parse_baseline` | детерминированный разбор фразы; понятое сразу входит в запрос сессии |
| `search` | поиск по накопленным желаниям; можно добавить пропущенные желания (`wishes`, проверка по схеме реестра), убрать (`remove`, выполняется до добавления), задать цену и звёзды. Перед поиском код прогоняет правило уточнения |
| `similar` | «похожий на этот / на второй / на Hotel X»; после него `search` отклоняется |
| `get_hotel` | факты уровня отеля с уверенностью |
| `ask_clarification` | запрос уточнения по фразе из `ambiguities` или ключу из `weak_importance`; система сама решает, задавать ли вопрос |
| `log_unmet_wish` | запись желания вне реестра с нормализацией и предложением характеристики; желание, которое парсер понимает, отклоняется |

Лимит как у сборщика: 20 вызовов модели на ход, после 5 отказов подряд модель останавливается (ход всё равно завершает код). Недоступность модели или промах кеша — ход повторяется по правилам (шаг `fallback_rules`, остальные записи журнала — `mode = rule`).

## Разбор фразы без LLM

Синонимы, значения и неоднозначные фразы лежат в реестре (`registry/*.yaml`, `docs/registry.md`), в коде только язык: маркеры важности («обязательно», «желательно», «важно»), отрицания («без», «не нужен»), числа и единицы (минуты, метры → минуты по скорости пешехода из стратегии, € , звёзды, этаж), служебные слова. Слово до 5 букв совпадает только целиком, длиннее — по первым пяти буквам: «500 метров до пляжа» не `walk_to_metro`, «в метре от моря» и «морской воздух» не `sea_view`, а `unmet_wishes`.

«У моря» и близкие фразы неоднозначны: по умолчанию `walk_to_beach` (10 минут), альтернатива — `sea_view`.

## Правило уточнения

Для каждой неоднозначной фразы код считает пробный поиск по каждой трактовке (с `NoDemand`: спрос не пишется) и сравнивает **упорядоченный топ-3**. Спросить можно, только если он различается, и не больше **1 вопроса на сообщение и 2 на сессию**. Иначе продолжаем с трактовкой по умолчанию, а допущение называем гостю («„У моря“ я поняла как „пляж рядом (до 10 минут)“; если нужно иначе — скажите»), если оно повлияло бы на выдачу. Если топ-3 не меняется, не спрашиваем и ничего не говорим.

То же правило применяется к мягкому маркеру важности («нужна тишина», «важно море»): гость мог иметь в виду и must, и prefer; сравниваются выдачи при обеих важностях. Важность, решённая вопросом или допущением, повторно не спрашивается.

Вопрос приходит событием `clarification` с кнопками (`options[].id`). Ответ — тот же `POST /api/chat` с `choice = id`. Если гость вместо кнопки написал новую фразу, берётся трактовка по умолчанию. Пример из проверки на рабочей БД: «Хочу тихий отель у моря, до 200 евро за ночь» → вопрос «„У моря“: важен вид из окна или пляж рядом (до 10 минут)?» (топ-3 при виде: 343, 155, 235; при пляже: 4, 3, 358); «важно тихо ночью» → топ-3 при must и prefer один и тот же, вопроса нет.

## Сессия: желания копятся

Состояние (`State`): накопленные желания и фильтры, этаж, последняя выдача (для «похожий на второй»), текущий отель, число заданных уточнений, висящее уточнение. «Без пляжа» убирает желание, «заново» сбрасывает запрос, «с 4-го этажа» применяется ко всем желаниям фасада, «похожий на этот / на второй / на Hotel X» запускает `similar` с весами из накопленных желаний и желаний не меняет. Профиль предпочтений живёт только на уровне сессии и в долгосрочный профиль не попадает.

### Почему сессия в Postgres, а не в памяти

Таблица `dialog_sessions(session_id, state jsonb, updated_at)`. Состояние в памяти процесса привязывало бы гостя к одному экземпляру сервера: за балансировщиком второй запрос попал бы на другой экземпляр и «забыл» разговор, а перезапуск или деплой стирал бы все диалоги. Масштабируемость — один из главных критериев, поэтому сервер остаётся без состояния и экземпляры взаимозаменяемы. Цена — один `SELECT` и один `UPSERT` на ход, при том что ход и так читает десятки фактов. Время жизни сессии — **1 час** после последнего обращения (`dialog.SessionTTL`); устаревшие строки удаляются при каждом чтении (`LoadState`), отдельного фонового процесса нет.

## Текст ответа и что в нём проверяется

Сообщение чата с выдачей короткое и **целиком строится кодом** (`shortResults`, `shortSimilar`): гость не читает проценты и источники, они есть на карточках под сообщением. Текст модели в него не попадает, поэтому модель не может сказать об отеле то, чего система не знает. Раньше вводную писала модель, и она однажды заявила «допускает размещение с питомцем» там, где по данным «данных нет»; проверка по числам, названиям и словам такую фразу пропускала.

```
Ищу: можно с питомцем (желательно); вид на море (желательно).
«У моря» я поняла как пляж в пределах 10 минут.          ← допущения разбора, если есть
Нашла 6 отелей:
1. Hotel Sofitel — Suite, 448 €
2. Bed and Beach — Deluxe, 142 €
Подробности по каждому — на карточках ниже.
```

- **«Ищу: …»** — желания из состояния сессии с важностью; фильтры по цене и звёздам.
- **Допущения и непонятое** — «„У моря“ я поняла как…», «Не учёл: …».
- **Список** — отели из `textHotels` (те же ранги, что у групп выдачи) с названием, лучшим вариантом номера и ценой (цена — мок). Заголовки групп («С питомцем можно, у пляжа, но ночью шумнее») в сообщение не входят: они остаются в блоке выдачи.
- Для «похожих» — «Похожие на X…» и список названий.
- `message.source` для выдачи всегда `template`; в интерфейсе у сообщения бейдж «шаблон».

Полный шаблонный текст по отелям (`resultsParts`: группы, статусы желаний, значения, уверенность, источники, `domain.ExplainHotel`) по-прежнему возвращается модели в результате инструмента `search` и показывается на карточках («Как выбрано»); сообщение гостю его не использует.

Модель по-прежнему разбирает запрос и выбирает инструменты, но текст выдачи не пишет, и просьбы «переписать вводную» (`retry_text`) больше нет. `VerifyIntro` и `finalText` остались в коде и тестируются как проверка пересказа, в ход выдачи они не включены.

## Журнал спроса `unmet_wishes`

Куски фразы, которым не нашлось характеристики, пишутся в `unmet_wishes(region_id, text, normalized, count, first_seen, last_seen, proposal jsonb)`. Нормализация: с моделью — каноническая форма, которую она передала в `log_unmet_wish`; без ключа — `domain.NormalizeUnmet` (слова без служебных, по первым пяти буквам, по алфавиту: «морской воздух» и «воздух морской» дают один ключ). Повтор той же нормализованной формы увеличивает `count`. `proposal` (предложение новой характеристики и способа её получить) только записывается и в реестр сам не попадает; без ключа он пуст. Запись делается в конце хода, поэтому откат на правила не удваивает счётчик. Ключи нормализации модели и слов могут не совпасть, тогда один спрос считается двумя строками: сведение — по `proposal.key` на этапе 8.

## API

`POST /api/chat`, тело `{"session_id": "...", "message": "...", "choice": "id кнопки", "hotel_id": 156}`: нужны `session_id` (до 64 символов) и `message` либо `choice`; `hotel_id` — открытый у гостя отель («похожий на этот»). Ответ — `text/event-stream`:

| Событие | Данные |
|---|---|
| `step` | решение агента: `n`, `mode` (`llm` / `cache` / `rule`), `decision`, `tool`, `input`, `output` — то же, что в `agent_trace` |
| `clarification` | `kind` (`ambiguity` / `importance`), `phrase`, `question`, `options[{id, label}]`; после него ход заканчивается |
| `results` | `kind: search` — `query`, `hotels` (как `/api/search`), `explanations[{hotel_id, headline, lines, notes}]`; `kind: similar` — `base`, `similar` (как `/api/hotels/{id}/similar`) |
| `message` | `text`, `source` (`template` / `llm`) |
| `done` | `session_id`, `mode`, `clarifications_asked` |
| `error` | только если сбой после начала потока; до него — обычный JSON с кодом 400 или 500 |

Спрос по ключу желания пишется один раз за сессию (правило 6.1); пробные поиски правила уточнения спрос не пишут.

## Журнал

Каждое решение пишется в `agent_trace` с `agent = 'guest_dialog'` и `session_id` диалога (`hotel_id` пуст): разбор, сравнение трактовок с топ-3 каждой, вопрос или допущение, вызовы инструментов моделью с аргументами и результатом, проверка текста, запись `unmet_wishes`, откат на правила. Режим записи: `llm` (живая модель), `cache` (ответ из кеша), `rule` (решил код). Для `make seed` такие строки не нужны: рецепт удаляет их перед дампом.

## Режимы и кеш

- Ключ задан — живая модель (`LLM_*`, любая OpenAI-совместимая, в том числе локальная).
- Ключа нет — `Replay` отвечает записанными ответами модели по хешу сообщений шага (`internal/adapter/llm/cache/dialog/*.json`, встроены в бинарник). Три записанных диалога: `clarify-beach` (уточнение, ответ кнопкой, дополнительное желание), `similar-hotel` («похожий на второй, но без вида на море»), `unmet-night` (непонятые желания, ночная аптека и метро, «важно тихо ночью» без вопроса, затем уточнение «у моря»).
- Промах кеша — этот ход выполняется по правилам: детерминированный парсер и шаблонные тексты (`mode = rule`).

Хеш включает системную подсказку и состояние сессии в первом сообщении, поэтому любое изменение подсказки, инструментов или формата результата инструментов делает записи устаревшими. Кеш диалога записан живой моделью на сиде в 8.3 вместе с кешами сборщика и интервьюера; после любой правки подсказки, инструментов или формата их ответов его нужно записать заново.

Запись: `go run ./cmd/collect dialog -session s1 -record имя "фраза" "@id_кнопки" "фраза 2"` (ключ в `.env`; `@id` — ответ кнопкой); проигрыш из кеша — `-cache`; только правила — `-rules`. Команда печатает те же события, что и SSE. Перед записью состояние сессии очищается. Прогон пишет спрос и `unmet_wishes` в рабочую БД, после записи демо их нужно убрать (`DELETE FROM characteristic_demand WHERE source = 'search'`, `demand_sessions`, `unmet_wishes`, `dialog_sessions`, `agent_trace` с `agent = 'guest_dialog'`).

## Ограничения

- Текст выдачи строит код (`shortResults`), текст модели в него не попадает; свойства отелей и статусы выводит шаблон по данным, смысл фраз модели код не проверял бы, поэтому модель их не пишет.
- Уточнений только два вида: неоднозначная фраза из реестра и мягкая важность. Вопросы вроде «на сколько человек номер?» не задаются: параметров состава гостей в запросе нет.
- Выдача диалога — 5 отелей; в тексте отели берутся по группам: до 3 подходящих по всем желаниям, до 2 «под вопросом» и до 2 в каждом из двух блоков компромиссов (`textHotels`).
- Нормализация `unmet_wishes` моделью и словами может разойтись (см. выше).
- Сравнение отелей, контракт ожиданий и бронь — `docs/compare.md`; интерфейс — этап 7.

## Демо-диалоги и реплей

Три демо-диалога лежат фикстурой `backend/internal/usecase/dialog/demo_dialogs.json` (встроена в бинарник): `clarify-beach` (у моря и с собакой → кнопка «пляж» → метро), `similar-hotel` («тихий отель с видом на море» → «похожий на второй, но без вида на море»), `unmet-night` (ночная аптека, метро, морской воздух → «у моря» → кнопка «пляж»). Ходы — реплики гостя, `@id` — ответ кнопкой.

- Запись кеша: `go run ./cmd/collect dialog -fixture имя -record имя` (ключ в `.env`; БД из сида — проект `clean-check`).
- `make test-replay-dialog` — проигрывает фикстуру из кеша без ключа в `clean-check`: ни один ход не должен перейти на правила (шаг `fallback_rules`), в каждом диалоге есть шаги из кеша. Последний прогон: 8 ходов, 0 промахов.
- `GET /api/dialog/examples` → `{"examples":[{"id","title","text"}]}` — первые фразы демо-диалогов для кнопок-примеров в чате (этап 7).

Кеш диалога записан на сиде 8.3 (8 ходов трёх демо-диалогов, 0 промахов); перезапись нужна после изменения подсказки или инструментов.
