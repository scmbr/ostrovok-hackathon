# Общение с отельером (этап 5, задача 5.2)

Агент-интервьюер (`backend/internal/usecase/hotelier`) спрашивает отельера только тогда, когда ответ что-то меняет:
один вопрос про характеристику отеля, ответ полезен всем будущим гостям. Значение факта агент записать не может:
ответ становится свидетельством отельера, факт собирает движок правды (`docs/truth.md`).

## Кандидаты

Вопрос возникает по характеристике с `ask_hotelier` в реестре, если:

- данных нет или уверенность факта ниже 0,6; либо
- у отеля открытый конфликт или `weak_disagreement`; либо
- у категории номеров название («Sea View», «Vista mar») спорит с расчётом (открытый конфликт `sea_view` категории).

Агент-сборщик (`collect agent`) тоже может предложить вопрос: он попадает в таблицу как кандидат `pending`, а решение об
отправке принимает интервьюер.

## Ценность вопроса

`ценность = спрос × неуверенность × влияние`, функции в `domain/question_value.go`.

- **Спрос** — `characteristic_demand.count`, нормированный на максимум в регионе. Пока это **мок** (`source = 'mock'`),
  на этапе 6 его пополняет поиск.
- **Неуверенность** `u = (1 − c) / (1 − 1/k)`, k — число значений (у bool 2); нет данных — 1; открытый конфликт добавляет
  0,3, `weak_disagreement` — 0,15; не больше 1.
- **Влияние** — 1, если хоть один возможный ответ меняет значение факта или переводит уверенность через 0,6 или 0,75
  (симуляция ответа с надёжностью `0,8 × (0,5 + trust)`, для выгодного отелю значения ещё `× 0,75`); нет данных — 1. У
  характеристик с правилом `category` берётся большее из этого и доли категорий отеля, у которых ответ меняет вероятность
  искомого значения (`AssessCategory`, у неуверенных фасадов значение переворачивается). Иначе вопросы по характеристикам
  уровня отеля не уходили бы никогда.

Порог отправки — **0,2**, бюджет — **3 отправленных вопроса на отель за 7 дней** (`domain.QuestionSendThreshold`,
`QuestionBudget`, `QuestionBudgetDays`; констант в реестре нет). Вопрос выше порога, не вошедший в бюджет, ждёт
(`pending`); ниже порога копится (`pending_low_value`).

**Вопросы по инициативе гостя (задача 6.3, `request.go`).** Подтверждение пожелания к брони («гость бронирует «Standard» с пожеланием «восточная сторона, этаж 4+»: можете гарантировать?», характеристика `wish_guarantee`, формат confirm) **не входит в недельный бюджет и в порог ценности**: бронь с пожеланием — естественный момент общения (PROJECT_CONTEXT, «Общение с отельером»), вопрос отправляется сразу. Он один на отель: открытый или копящийся вопрос переиспользуется, а если отельер уже отвечал, вопрос не создаётся. Ответ «да» даёт свидетельство `wish_guarantee = true` (вероятность выполнения пожелания у следующих гостей 0,95), «нет» — `false` (0,4), без ответа — 0,7 (`docs/search.md`). Кнопка «спросить отель» в контракте ожиданий бюджет **не обходит**: это обычный раунд интервьюера (ценность, порог, бюджет), только запущенный по просьбе гостя; живой вопрос по той же характеристике, в том числе по категории, переиспользуется. Подробности — `docs/compare.md`.

## Статусы

| Статус | Значение |
| --- | --- |
| `pending` | прошёл порог, ждёт бюджета |
| `pending_low_value` | ниже порога, копится |
| `open` | отправлен, ждёт ответа (в дайджесте) |
| `needs_clarification` | ответ получен, значение не найдено; значение не выдумывается |
| `answered` | значение найдено, свидетельство записано |
| `closed` | данные появились сами |

## Формат вопроса

- `confirm` — если есть расчёт: «по расчёту из номеров „Vista mar“ (фасад на восток, во двор, этажи 2–5) море не
  видно — верно? (да / нет / уточнить)». Текст формулирует LLM по шаблону, ответ в кеш; если модель потеряла «верно?»,
  берётся шаблон.
- `open` — если расчёта нет: конкретный вопрос из реестра («из каких категорий, на какую сторону, с какого этажа»).

## Разбор ответа

- `confirm`: «да» подтверждает расчёт. «Нет» у характеристики с двумя значениями (bool, enum из двух, `full / none` у
  категории) даёт противоположное значение: признание недостатка у честного, спор с расчётом у приукрашивающего. «Нет» при
  большем числе значений (`noise_night`), диапазоне и «уточнить» значения не дают, вопрос возвращается в `open` с
  уточнением «как на самом деле?».
- `open`: LLM раскладывает текст по схеме характеристики (допустимые значения из реестра), ответ проверяется, одна попытка
  исправления; без ключа и при промахе кеша — разбор «да / нет» и деталей (виды, вес, цена) по шаблонам. Детали лежат в
  `claimed.details` и не голосуют.

Свидетельство отельера: `author_id` = id отеля, текст ответа в `details`, метод `hotelier_answer@1`. Новое утверждение
того же автора по той же сущности и характеристике заменяет прежнее (`superseded`), в том числе название «Sea View» из
мока. Размещения номеров (`room_placements`) из свободных ответов пока не разбираются.

## Репутация

После каждого ответа `usecase/reputation` пересчитывает `author_trust` заново по всем активным свидетельствам автора: `trust = (совпадения + 1) / (всего + 2)`. **Судья утверждения — факт без автора** (`docs/truth.md`): он собирается движком правды из свидетельств других авторов той же сущности и характеристики (расчёт, гости, ...) и служит судьёй при уверенности не ниже `domain.ConfidentFact` = 0,75. Совпало значение — совпадение, нет — расхождение; сила расхождения не важна; числа и структуры не сравниваются; нет судьи — утверждение не считается. Если вес автора изменился, его факты пересобираются.

Порядок при ответе: записать свидетельство → пересчитать репутацию (судья от неё не зависит) → **одна** сборка факта (или пересборка всех фактов автора, если репутация изменилась). Промежуточной сборки со старым доверием нет.

Примеры на данных: 326, «Sea View» против расчёта (судья — только расчёт, 0,85): `trust` 0,50 → 0,33, уверенность непроверяемых утверждений отеля 0,60 → 0,50. 156: судья — гости и расчёт (`none`, ≈ 0,94); «Sea View» (`full`) против него — `trust` 0,50 (1 из 2), после честного «нет» — 0,75 (2 из 2). Ограничение: если расчёт слаб или источники спорят (уверенность судьи < 0,75), приукрашивание остаётся конфликтом, но репутацию не меняет.

**Сид и правило согласованы (8.3).** `collect reputation-recompute` выполнен после анкет, сигнала и пересчёта, поэтому `author_trust` в сиде лежит по текущему правилу: у 156 0,50 → 0,75 после «нет», у 326 с самого начала 0,33 (спор по названию категории снят расчётом). Проверка правила: `collect reputation-recompute` пересчитывает репутацию всех отельеров и печатает изменившиеся.

## Имитированные отельеры (мок)

У демо-отелей `hotels.hotelier_persona`. Тексты ответов — детерминированный генератор (`domain.PersonaAnswer`), без LLM.

- `honest` отвечает полно по скрытой истине и признаёт недостатки;
- `lazy` отвечает коротко и неполно («да, с собаками можно» без веса и цены), примерно в каждом шестом случае уходит от
  ответа («не уверен, надо уточнить»);
- `embellishing` подтверждает благоприятное независимо от истины и расчёта и оспаривает невыгодный расчёт. Это отели с
  «Sea View» без вида из `collect mock-rooms` (определяются по открытому конфликту, как в `collect stats`).

Скрытая истина по непроверяемым характеристикам (`mock_hotel_truth`: питомцы у ~30 % отелей, затемняющие шторы у ~60 %)
и спрос — **моки** (`collect mock-hotelier`). Истина не свидетельство и в рантайме не читается; она нужна персонам и
оценке точности на этапе 8.

## Команды и API

```sh
cd backend
go run ./cmd/collect mock-hotelier                 # персоны, спрос и истина (после mock-rooms)
go run ./cmd/collect hotelier-round -hotel 57      # раунд: вопросы по ценности и бюджету, ответ персоны, разбор
go run ./cmd/collect hotelier-round -answer=false  # только отправить: вопросы остаются в дайджесте
go run ./cmd/collect hotelier-preview              # разбор ответа персоны на открытые вопросы без записи в БД (ответы LLM — в кеш)
go run ./cmd/collect hotelier-reset                # снять вопросы, ответы, репутацию и пересобрать факты
```

Конфликт категории, в котором есть ответы гостей против расчёта (`docs/guests.md`), попадает в вопрос с их числом и
возможными причинами («деревья, строительные леса, стройка?»), остаётся подтверждением расчёта (да / нет / уточнить).
Приукрашивающими (`mock-hotelier`) считаются только отели, где против расчёта стоит название категории; конфликт с
гостями приукрашиванием не считается.

Режимы LLM: ключ задан — живая модель с записью ответов в `adapter/llm/cache/hotelier/`, нет ключа или `-cache` — кеш,
при промахе шаблоны; `-no-llm` — только шаблоны. Журнал решений — `agent_trace`, `agent = 'hotelier_interviewer'`.

| Маршрут | Назначение |
| --- | --- |
| `GET /api/hotelier/{hotel_id}/inbox` | дайджест: отправленные вопросы по ценности с причиной, бюджет, число копящихся |
| `POST /api/hotelier/questions/{id}/answer` | ответ: `{"text": "…"}` или `{"answer": "yes"\|"no"}` |
| `POST /api/hotelier/questions/{id}/persona-preview` | ответ имитированной персоны и его разбор (`parsed_by`) без записи в БД; у отеля без персоны — 409 |
| `POST /api/hotelier/facts/{id}/confirm` | подтвердить факт: свидетельство отельера с тем же значением |
| `POST /api/hotelier/facts/{id}/correct` | исправить: `{"value": "…", "details": {…}}`; у чисел значение не меняется, факт ставится на пересчёт |
| `POST /api/hotelier/hotels/{hotel_id}/facts/confirm\|correct` | то же по адресу `{"entity_type", "entity_id", "key", "value"}`: id факта меняется при пересборке, адрес — нет; отель проверяется |
| `GET /api/hotelier/hotels` | демо-отели с персоной (переключатель роли) |
| `GET /api/hotelier/{hotel_id}/demand` | упущенный спрос: характеристики, которые искали гости, а у отеля их нет или уверенность ниже 0,6 |

## Кабинет отельера (этап 7, задача 7.2a)

Экран `/hotelier?role=hotelier&hotel=ID` (отель выбирается в списке: сначала отели сценариев 326, 156, 161, 188, 343, 177, 57, 143, остальные — поиском).

- **Дайджест** — вопросы по ценности с причиной (`reason_kind`: нет данных / низкая уверенность / расчёт спорит с отелем / гости сообщили иное / утверждение отеля не подтверждено расчётом: спор по категории уже снят, текст причины строится по текущему состоянию, сохранённый текст вопроса не меняется), спросом и форматом (confirm — «да / нет / уточнить», open — текст). Счётчик: «на этой неделе N из 3, ещё M ждут своей очереди». Подтверждения пожеланий из броней (`wish_guarantee`) идут отдельным блоком «Пожелания гостей к брони» с данными брони и **в недельный бюджет не входят** (`SentSince` их не считает).
- **Результат ответа** (`change` в ответе `answer` и правок фактов): факт до и после записи свидетельства и **пересчёта репутации в том же запросе** (репутация считается синхронно, асинхронных пересчётов нет), свидетельства с вкладами, конфликт (`opened / closed / remains / none`), `author_trust` до → после. Итог тот, что даёт движок правды, даже если он не в пользу отельера.
- **«Ответить как персона»** — `persona-preview`: ответ персоны и разбор тем же путём, что при отправке (`Preview` и `processAnswer` вызывают один `Parse`), поэтому запрос к модели и результат совпадают. Без ключа вопросы формата confirm разбираются правилом да / нет, открытые — из кеша интервьюера, при промахе — запасным разбором.
- **«Что система знает»** — факты отеля, фасадов и категорий (`FactCard` со свидетельствами), «подтвердить» и «исправить» по адресу сущность + характеристика.
- **Упущенный спрос** — по `characteristic_demand` (мок + поиск) там, где у отеля данных нет или уверенность ниже 0,6.
- **Закрытый конфликт**: в `change.resolution` приходит причина (`agreed` / `weight_dropped` / …, см. `docs/truth.md`). При `weight_dropped` интерфейс пишет «Спор снят в пользу расчёта: доверие к утверждениям отеля снизилось (0,50 → 0,33), их вес в пользу отеля теперь ≈ 0», а не «конфликт закрыт». Свидетельства человека с нулевым вкладом в «что система знает» помечены «вес ≈ 0: мало доверия к утверждениям отеля в его пользу».
- **Комментарий к ответу.** У «да» / «нет» есть необязательное поле комментария (`{"answer": "no", "comment": "…"}`, до 500 символов). Значение даёт кнопка правилом, комментарий не разбирается и в запрос к модели не попадает; он сохраняется в `evidence.details` (`button`, `comment`, `answer_text` — слово-кнопка) и показывается «со слов отеля: «…»» в результате ответа, в «что система знает» и в карточке отеля у гостя. «Уточнить» со свободным текстом у `range` без модели честно уходит в `needs_clarification`.
- **Пометка о доверии** (`trust_note`) отдаётся и в `GET /api/hotels/{id}` (факты отеля и факты категорий) тем же `domain.TrustNote`, что в выдаче.

## Настройка демо-сценария: даты вопросов отеля 156

В сиде у отеля 156 Serras Hotel Barcelona (сценарий closed_view, `docs/guests.md`) три прежних вопроса интервьюера
(шторы, `noise_night`, питомцы) помечены как отправленные и отвеченные 8 дней назад: сдвинуты `asked_at`, `sent_at` и
`answered_at` у этих трёх строк `hotelier_questions`. Зачем: бюджет отельера — 3 вопроса в неделю, три вопроса уже
использовали его, и вопрос по конфликту «гости против расчёта» остался бы `pending`, а не `open`. Со сдвигом он попадает
в дайджест, и на нём можно показать живой ответ в кабинете («деревья, леса, стройка»). Это настройка демо, а не
поведение системы; в бэклоге — правило, по которому вопрос по открытому конфликту с высокой ценностью может превысить
недельный бюджет на один.

## Подтверждение расчёта по категории после снятия спора

Вопрос формата confirm по категории («по расчёту из номеров „Sea View“ море не видно — верно?») подтверждает **расчётное свидетельство категории** (`room_projection`), а не итоговый факт и не только спорные категории. Раньше значение бралось из категорий с открытым конфликтом: после того как вес приукрашивающего отельера упал до нуля (`weight_dropped`, см. 326) конфликт закрывался, категория выпадала из списка, и ответ «нет» превращался в «неясно» без записи. Теперь «нет» даёт значение, противоположное расчёту, «да» подтверждает расчёт, а без расчётного свидетельства остаётся прежнее уточнение. Для 326 в сиде: ответ приукрашивающей персоны записывает `full`, доверие остаётся 0,33 → 0,33, вклад ≈ 0, факт категории `none` 0,85 не меняется, конфликт не открывается (`conflict_change: none`).

## Известный дефект: кандидаты `wish_guarantee`

Раунд интервьюера (`hotelier-round`) создаёт кандидата `wish_guarantee` для каждого отеля (статус `pending_low_value`, ценность 0), хотя характеристика нужна только из броней с пожеланием (`ConfirmWish`). Агент-сборщик создаёт такого кандидата со статусом `pending` у отелей, которые прогоняет (161, 177, 188, 279, 343). В сиде 61 строка `pending_low_value` **удалена вручную** (SQL `DELETE FROM hotelier_questions WHERE characteristic_key = 'wish_guarantee' AND status = 'pending_low_value'` после раундов); пять `pending` оставлены: бронь с пожеланием переиспользует копящийся вопрос и сразу отправляет его. Повторный раунд снова создаст строки. Для метрик (8.2) «доля вопросов, отсеянных ценностью и бюджетом» считается **без** вопросов `wish_guarantee`.
