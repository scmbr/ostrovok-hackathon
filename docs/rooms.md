# Категории номеров: от фасадов к вероятности

Черновик раздела для README. Реализация — `backend/internal/domain/rooms.go` (чистая функция `AssessCategory`, тесты в `rooms_test.go`), расчёт свидетельств категорий — `backend/internal/usecase/rooms`, мок — `backend/internal/usecase/collect/mock_rooms.go`.

## Зачем

Островок продаёт **категории** номеров, а номер внутри категории отель выбирает при заселении. Факты у нас по фасадам и этажам («с востока море видно с 4-го этажа»). Чтобы честно сказать гостю, что он получит, значение переносится на категорию как **вероятность**, **гарантия** и **пожелание** к брони.

## Данные

- `room_categories(id, hotel_id, name, rooms_count)` — категория и число её номеров.
- `room_placements(room_category_id, facade_id, floor_from, floor_to, rooms_count, source, confidence, evidence_id)` — размещение: сколько номеров категории на этом фасаде в этих этажах. Сумма `rooms_count` по размещениям равна `room_categories.rooms_count`.
- Размещение сообщает **отельер**. Оно хранится свидетельством (`evidence`: `characteristic_key = room_placement`, `author_type = hotelier`, одно на категорию), строки `room_placements` ссылаются на него; итоговый факт `room_placement` лежит в `facts`. Сейчас отельера имитирует `collect mock-rooms`.

## Вероятность, гарантия, пожелание

Для категории из `N` номеров, размещения и значения характеристики у фасада на этаже (`AssessCategory`):

- номера размещения делятся по его этажам **поровну** (6 номеров на этажах 2–6 — по 1,2 на этаж);
- **вероятность** значения — доля номеров категории с ним (`Probability`, для искомого значения `Target`); номера не размещённые или у фасадов без факта — `Unknown`;
- **гарантия** — все номера категории размещены и имеют искомое значение; иначе — шанс;
- **пожелание** — «фасад X, этаж N+»: фасад, где под условием окажется больше всего номеров категории; N — наименьший этаж, начиная с которого на фасаде у всех номеров категории искомое значение (0 — этаж не важен). Если гарантия есть, пожелание не нужно.

Пример из контекста: «Стандарт», 20 номеров, 6 из них на востоке, этажи 2–6. Море видно с 4-го этажа: 3 этажа из 5, `6 × 3/5 = 3,6` номера, **18 %**; с 3-го этажа — `6 × 4/5 = 4,8`, **24 %** (это и есть «~25 %» из описания). Пожелание «восточная сторона, этаж 4+» покрывает 18 % номеров категории. Тесты: `TestAssessCategoryContextExample`, `TestAssessCategoryWish`.

## Какие характеристики переносятся

Те, у которых в реестре есть блок `category` (`registry.md`): сейчас `sea_view` (`full / none`; фасад видит море с этажа `min_floor`, ниже — `none`) и `noise_night` (преобладающий уровень по фасадам, этаж не важен). Новая характеристика уровня фасада переносится на категории добавлением блока, без нового кода.

`collect rooms` для каждой категории записывает **расчётное свидетельство** (`source = computed`, `author = room_projection@1`): значение — преобладающее среди номеров, в `claimed` — вероятность, гарантия, доли, пожелание. Надёжность = средняя уверенность фактов фасадов (по числу номеров) × доля номеров с преобладающим значением: чем смешаннее категория, тем слабее утверждение.

## Название категории — утверждение отеля

Название «Sea View» / «Vista mar» (`TitleClaimsSeaView`) — не факт, а утверждение отеля. Когда категория с таким названием записывается (`SaveHotelRooms`), к ней добавляется свидетельство отельера `sea_view = full`: база 0,8, асимметрия ×0,75 (вид — выгодное значение), итог `r = 0,6`, вклад `ln(0,6/0,4) = 0,41`.

Дальше работает обычный движок правды (`truth.md`):

- расчёт согласен (вид есть на всех номерах, `r ≈ 0,8…0,85`): факт `full`, уверенность выше расчётной, конфликта нет;
- расчёт против (`none`, `r = 0,85`, вклад 1,73): обе стороны весят не меньше порога, **конфликт**; значение факта — `none`, уверенность 0,79.

Порог `θ` для категории задан в реестре отдельно (`category.conflict_theta: 0.3`): при общем `θ = 1,0` слабое по определению утверждение отельера в свою пользу (0,41) не создало бы конфликта никогда. Расчёт при этом должен быть уверенно против, иначе «против» не наберёт и 0,3.

## Мок

`collect mock-rooms` (после `mock-cards` и `sea-view`), детерминированно от `hotels.id`, только для демо-отелей с фасадами:

- обычные категории берутся из мок-карточки, номеров 24–60 в «Standard», 14–30 в «Superior», 8–20 в «Deluxe», 6–16 в «Family», 4–10 в «Suite»; размещение — по 1–3 случайным фасадам, диапазон этажей в пределах этажности фасада, не больше 8 номеров на этаж, пока хватает этажей;
- у берегового отеля (до 400 м от берега), у которого расчёт даёт вид хотя бы с одного фасада, добавляется честная «Sea View» или «Vista mar» (по чётности id): 6–15 номеров на фасадах с видом, начиная с этажа начала вида — гарантия;
- у трёх береговых отелей без вида на море ни с одного фасада (три первых по хешу id, `PickBeautifiers`) «Sea View» размещена на фасадах, где `sea_view = none` на всех этажах: материал для демо приукрашивающего отельера. `collect stats` печатает такие категории (открытые конфликты `sea_view` у `room_category`).

Все эти данные — мок (персона отельера пишется в `evidence.details.persona`: `honest` / `embellishing`) и не отражают реальные отели.

## API

`GET /api/hotels/{id}/rooms` — категории отеля, размещение (с фасадами и сторонами света), по каждой характеристике: вероятность, гарантия, доли значений, пожелание текстом («восточная сторона, этаж 4+») и итоговый факт движка правды со свидетельствами и конфликтом. Вероятность и пожелание считаются по текущим фактам фасадов, значение и уверенность берутся из `facts`. Нет категорий — 404.

## Ограничения

- Расчётные свидетельства категорий пересчитываются командой `collect rooms`; при пересчёте `sea_view` или `noise_night` по фасадам они устаревают до следующего запуска (автоматический пересчёт — задача актуализации).
- Модель «номера делятся по этажам поровну» грубая: реальный отель знает распределение точнее; уточнять будет вопрос отельеру.
- `partial` для вида на море не вводился: фасад либо видит море (`full`), либо нет (`none`).
- Угловые номера (два фасада) пока не моделируются: номер относится к одному фасаду.
