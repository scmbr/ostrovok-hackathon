# Реестр характеристик

Характеристика — один YAML-файл `backend/registry/<key>.yaml`. Реестр встраивается в бинарник (`go:embed`), проверяется на старте сервера и в каждой команде `collect`; ошибка реестра останавливает запуск. Список для клиентов: `GET /api/characteristics`.

Новая характеристика добавляется файлом или текстом (`collect add-characteristic`). Новый код нужен, только если не подходит ни один существующий инструмент.

## Поля

| Поле | Смысл |
|---|---|
| `key` | snake_case латиницей, совпадает с именем файла |
| `title`, `description` | название и смысл |
| `level` | `hotel`, `facade`, `district` — к чему относится значение |
| `value_type` | `bool`, `enum`, `number`, `range`, `text`. `range` и `text` — структура (этаж, помесячная таблица): значения не сравниваются, берётся сильнейшее свидетельство |
| `values`, `ordered` | значения enum; `ordered: true` — они идут по ступеням |
| `value_field` | поле значения в `evidence.claimed` (по умолчанию `value`) |
| `ttl_days` | срок годности свидетельства, после него факт `stale` и ставится на пересчёт |
| `favorable_values` | значения, выгодные отелю: к утверждению отельера о них применяется асимметрия ×0,75 |
| `significant_diff` | только `number`: расхождение меньше — «одинаково»; больше — «против» |
| `conflict_steps`, `conflict_theta`, `conflict_entities` | правила конфликта (см. `truth.md`); по умолчанию 1 ступень, θ = 1,0, все сущности |
| `category` | необязательный блок: как характеристика уровня `facade` читается в категории номеров (см. `rooms.md`). Поля: `values` (значения у категории), `ordered`, `value_field` (поле значения в свидетельстве категории), `target` (искомое значение), `floor_field` (поле факта фасада с этажом, с которого выполняется `target`; ниже — последнее из `values`; без него значение берётся из поля самой характеристики и `values` совпадают с её `values`), `favorable_values`, `conflict_steps`, `conflict_theta`, `conflict_theta_hotelier` (пониженный θ, только если в споре участвует свидетельство отельера) — правила движка правды для категории. Есть у `sea_view` и `noise_night` |
| `strategies` | как получать значение, по порядку |
| `ask_hotelier`, `ask_guest` | вопрос отельеру и вопрос гостю в анкете после проживания |
| `origin`, `origin_text`, `added_at` | необязательные: `origin: text` — характеристика добавлена текстом, `origin_text` — исходная фраза, `added_at` — дата `YYYY-MM-DD`. Команда `add-characteristic` заполняет их сама; без `origin` двух других полей быть не должно |

Стратегия:

| Поле | Смысл |
|---|---|
| `tool` | инструмент из `collect tools` |
| `strategy` | вариант инструмента, обязателен, если у инструмента несколько источников (`noise-night`: `bcn`, `osm`) |
| `params` | параметры инструмента: числа и наборы (`kinds: [pharmacy]`); поверх умолчаний инструмента, но ниже `-param` в командной строке |
| `base_reliability` | база надёжности свидетельства из (0; 1); у `sea_view` это потолок, понижение по качеству высот остаётся в расчёте |
| `independence_group` | источники одной группы считаются один раз |

Если стратегий нет, значение можно получить только от отельера: `ask_hotelier` обязателен.

## Проверка при старте

Инструмент существует и считает эту характеристику (универсальные инструменты — любую); параметры и значения наборов допустимы; `level` совместим с областью инструмента (по отелям или по районам); `values`, `favorable_values`, `conflict_steps` согласованы с `value_type`; `significant_diff` задан у `number`; `base_reliability` в (0; 1), `independence_group` не пуст; у разных характеристик один числовой параметр инструмента (например, скорость пешехода у `walk`) не имеет разных значений. Ошибки печатаются все сразу.

## Универсальные инструменты

`night-services` считает любую характеристику, чья стратегия на него ссылается, с набором `kinds` (`pharmacy`, `shop`, `food`; по умолчанию все). Один запуск `collect night-services` пересчитывает `night_services` и все добавленные по тому же образцу. Так «ночная аптека» появляется без нового кода: `night_pharmacy` лежит в реестре как пример характеристики, добавленной текстом (`origin: text`).

## Добавление текстом

```
cd backend
go run ./cmd/collect add-characteristic "Есть ли рядом круглосуточная аптека?"
go run ./cmd/collect add-characteristic -dry-run "..."   # только показать YAML
```

1. LLM получает правила, пример и каталог инструментов (`Spec`: параметры, варианты, значения наборов) и возвращает YAML. Выбирать она может только из каталога; если инструмента нет, стратегий нет, а вопрос отельеру обязателен.
2. Ответ проходит ту же проверку, что и реестр на старте, вместе со всем реестром. Не прошёл — LLM один раз получает свой ответ и список ошибок. Второй неудачный ответ — ошибка с замечаниями.
3. Надёжность и группу независимости LLM не выбирает: для инструмента (и варианта), который уже есть в реестре, они берутся оттуда; правка печатается.
4. Файл пишется в `backend/registry/<key>.yaml`. Реестр встроен в бинарник, поэтому сервер нужно пересобрать; значения считает `collect <инструмент>`.

LLM описывает, как получать характеристику, и не пишет значений: факты по-прежнему только свидетельства инструментов, отельеров и гостей.

### Режим кеша

Без `LLM_API_KEY` команда отвечает заготовками из `backend/internal/adapter/llm/cache/*.yaml`: «есть ли рядом круглосуточная аптека» (`night_pharmacy`, инструмент `night-services` с `kinds: [pharmacy]`), «есть ли рядом круглосуточный магазин» (`night_shop`, `kinds: [shop]`; для живого демо, в реестре его нет), «можно ли с собакой» (`pets_allowed`, bool, только вопрос отельеру), «затемняющие шторы» (`blackout_curtains`, только вопрос отельеру). Совпадение по нормализованному тексту (регистр, ё, знаки препинания), по целым словам. Для другого текста команда называет доступные заготовки. Заготовки проходят ту же проверку, что и ответы живой модели (тест `TestCannedAnswersPassRegistryValidation`).

С ключом используется `LLM_BASE_URL` (OpenAI, Ollama, vLLM), `LLM_MODEL`; температура 0.
