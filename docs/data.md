## OpenStreetMap (Overpass API)

- **Что:** отели (`tourism=hotel`), здания (`building=*`, с `building:levels` и `height`), береговая линия (`natural=coastline`).
- **Откуда:** публичные зеркала Overpass: `overpass-api.de`, затем `overpass.kumi.systems`, `maps.mail.ru`. Запросы идут с осмысленным `User-Agent`, иначе серверы отвечают 406/429.
- **Когда:** 24.10.2026.
- **Как воспроизвести:** `docker compose up -d db`, затем `cd backend && go run ./cmd/collect osm`. Команда идемпотентна: здания и отели обновляются по `osm_id`, береговая линия заменяется целиком.
- **Лицензия:** ODbL 1.0, © участники OpenStreetMap. При публикации нужна атрибуция «© OpenStreetMap contributors».

Запросы (границы `S,W,N,E`, районы из `internal/domain/geo.go`):

| Данные    | Запрос Overpass QL                                                              | Область                                    |
| --------- | ------------------------------------------------------------------------------- | ------------------------------------------ |
| Отели     | `nwr["tourism"="hotel"](bbox);out center tags;` для каждого из шести районов    | районы из таблицы ниже                     |
| Здания    | `way["building"](bbox);out geom tags;`                                          | объединение районов + 0,003° (~300 м)      |
| Береговая | `way["natural"="coastline"](bbox);out geom;`                                    | объединение районов + 0,01° (~1 км)        |

Результат на 24.10.2026: 209 отелей, 17 105 зданий OSM, 42 отрезка береговой линии.

### Береговые отели

Отель считается береговым, если расстояние до береговой линии (таблица `sea`, `ST_DWithin` по `geography`) не больше `CoastalRadiusM` = 400 м. В OSM (`tourism=hotel`) отелей по расстоянию до берега:

| Радиус | Береговых отелей |
| ------ | ---------------- |
| 300 м  | 14               |
| 400 м  | 22               |
| 500 м  | 31               |

Цель этапа 2 — не меньше 20 отелей «в пределах ~300 м»; на 300 м набирается только 14, поэтому радиус принят 400 м (решение зафиксировано 24.10.2026). Остальные источники жилья (`hostel`, `apartment`, `guest_house`) не добавлялись.

Правила разбора:

- Отель без `name` и отель-relation пропускаются; район определяется по точке (для way — по центру).
- `osm_id` отеля-way хранится с минусом: id узлов и путей в OSM пересекаются.
- Высота здания: `height` → `osm_height`; иначе `building:levels` × 3 м → `osm_levels`; иначе 15 м → `default`. Футы и нечисловые значения игнорируются.
- Отель-way связывается со зданием с тем же id; отель-узел — со зданием, в которое попадает точка.

Известные ограничения:

- Здания-relation (мультиполигоны) пока не загружаются, внутренние дворы (дырки) тоже. Из-за этого у 76 из 209 отелей нет здания OSM (`osm_building_id`); основное здание (`building_id`) берётся из кадастра.
- У 5 126 из 17 105 зданий OSM высоты нет (`default`).
- Отели-relation и отели без `name` пропускаются (17 при последней выгрузке).

## Дороги OSM и фасады отелей (этап 2)

### Дороги

- **Что:** `way["highway"~"^(motorway|trunk|primary|secondary|tertiary|unclassified|residential|living_street|pedestrian|*_link)$"]`, `out geom tags;`, область — объединение районов + 0,003°. Тропинки, лестницы, велодорожки и служебные проезды (`service`) не берутся.
- **Когда, откуда, лицензия:** 24.10.2026, те же зеркала Overpass, ODbL 1.0, © участники OpenStreetMap.
- **Команда:** `cd backend && go run ./cmd/collect roads` (после `osm`: нужны отели). Идемпотентна: таблица `roads` заменяется целиком.
- **Отбор:** сохраняются только дороги не дальше 300 м от какого-либо отеля (`RoadsRadiusM`, `ST_DWithin` по `geography`), чтобы не раздувать сид. Результат: 3 324 дороги.

### Фасады

- **Что:** сторона основного здания отеля (`hotels.building_id`, в основном кадастр) с азимутом внешней нормали (куда смотрят окна, от севера по часовой), длиной, признаком `faces_street` и `courtyard` (фасад по внутреннему кольцу). Таблица `facades`.
- **Команда:** `cd backend && go run ./cmd/collect facades` (около 70 секунд на 209 отелей). Пересчёт идемпотентен: фасады отеля заменяются целиком.
- **Алгоритм** (геометрия — `internal/domain/facade.go`, выборки — PostGIS в `adapter/repository/postgres/facades.go`):
  1. Контур делится на рёбра; внешнее кольцо обходится против часовой стрелки, внутренние по часовой, поэтому внешняя нормаль всегда справа.
  2. Дворы площадью меньше 30 м² (световые колодцы) пропускаются целиком.
  3. **Глухие стены.** Ребро, у которого не меньше половины центральной части лежит не дальше 1,5 м от контура соседнего здания (кадастр и OSM, кроме самого здания отеля и его дубликата из другого источника), — стена соседа, фасадом не становится. Проверка в SQL. Меряется центральная половина ребра, а допуск сужается до четверти длины: иначе буфер угла соседнего здания, лишь касающегося короткого фасада узкого дома, накрывал бы его целиком. Первая версия без этого давала 9 отелей без уличного фасада вместо 5 и 57% глухих рёбер вместо 45%.
  4. Подряд идущие не глухие рёбра склеиваются в фасад, если поворот между соседними меньше 10° и отклонение от первого ребра меньше 20°. Азимут — по хорде.
  5. Фасады короче 3 м (внешние) и 8 м (дворовые) отбрасываются.
  6. **Улица или двор.** Луч от середины фасада наружу на 25 м (`StreetProbeM`). Улица, если он пересёк дорогу раньше, чем упёрся в здание (сосед или само здание отеля). Всё, что не улица, — двор или тупик.
- **Результат на 24.10.2026** (209 отелей):

| Показатель                                         | Значение                       |
| -------------------------------------------------- | ------------------------------ |
| Фасадов                                            | 1 185 у 208 отелей             |
| Из них на улицу / по контуру двора                 | 444 / 35                       |
| Рёбер контура / отброшено как глухие стены         | 6 433 / 2 873 (44,7%)          |
| Отелей без фасада на улицу после исключения глухих | 5 (из них в демо 2)            |

- **Отели без фасада на улицу** (список выводит `collect stats`; это сигнал проблемы с данными, а не ошибка отбора, причины не проверялись):
  - Hotel BestPrice Diagonal (демо): 3 фасада, дорога из выгрузки не ближе 39 м от точки отеля;
  - H10 Catalunya Plaza (демо): 1 фасад, 21 из 24 рёбер глухие;
  - HCC Taber: фасадов нет, 26 из 27 рёбер глухие;
  - Hotel Barcelona Catedral: 4 фасада, дорога в 22 м от точки отеля;
  - Roma Reial: 2 фасада, дорога в 14 м от точки отеля.
- **Проверка на месте** (выборочно): у Hotel Arts, здания повёрнутого на 45° вместе с сеткой Серда, стороны на 45/135/225/315°; фасады на юго-восток (135°, к морю) не помечены как улица. Формальная проверка на 5 известных отелях — следующая задача этапа.
- **Ограничения:**
  - здание отеля берётся как один контур; отель, занимающий несколько смежных участков кадастра, видит стены между ними как глухие;
  - улицей считаются только дороги из `roads` (без `service`, тропинок и площадей-полигонов), поэтому фасады на пешеходные площади и служебные проезды могут быть помечены как двор;
  - допуск глухой стены для коротких рёбер (меньше 6 м) уменьшается; параллельная стена соседа на расстоянии 1,5 м от короткого ребра может быть не замечена.

## Вид на море (`sea_view`, этап 2)

Первая вычисляемая характеристика: с какого этажа фасад видит море. Хранится в `facts` (`source = computed`, `method = sea_view_raycast@1`), для каждого факта заполнены `confidence`, `observed_at`, `valid_until` (год) и `evidence`.

- **Команда:** `cd backend && go run ./cmd/collect sea-view` (после `facades`). Считает все отели с фасадами; на 208 отелей около 3,5 минут. Пересчёт переводит прежние активные факты в `superseded`. При пересчёте фасадов (`facades`) факты о старых фасадах тоже закрываются.
- **Входные данные:** береговая линия OSM (`sea`); препятствия — части зданий кадастра с разной этажностью (`building_parts`), здания кадастра без частей (этажи × 3 м) и здания OSM, не перекрытые кадастром (`buildings.shadowed = false`; дубликатом считается здание OSM, больше половины площади которого перекрыто зданием кадастра, таких 15 850 из 17 105).
- **Алгоритм** (геометрия лучей — PostGIS, `adapter/repository/postgres/sea_view.go`; видимость по этажам — Go, `domain/sea_view.go`):
  1. От середины фасада, отодвинутой на 0,5 м наружу, идёт веер из 19 лучей (±45° от внешней нормали, шаг 5°), длиной до 1,5 км.
  2. Луч «упирается в море» в ближайшей точке пересечения с береговой линией, где он идёт с суши в воду (вода справа от направления линии OSM).
  3. По пути до берега берутся все препятствия, пересекающие луч (включая части самого здания отеля, если фасад в нише): расстояние, высота, источник высоты.
  4. Этаж `f` видит луч, если ни одно здание не выше линии взгляда от окна (высота `(f−1)·3 + 1,5 м`) до точки воды в 150 м за береговой линией: `H_здания ≤ h·(1 − d/(D+150))`.
  5. Этаж «имеет вид», если море видно не менее чем по 25% лучей. `min_floor` — наименьший такой этаж (пусто, если вида нет ни с одного этажа этажности здания).
- **Факты:** по фасаду `{min_floor, levels, view_fraction по этажам, nearest_water_m}`; по отелю — лучший фасад: наименьший `min_floor` среди фасадов, чья этажность не меньше половины максимальной по отелю (фасад подиума под башней номеров, скорее всего, не имеет), при равенстве шире обзор: `{min_floor, levels, facade_id, azimuth_deg, facades_with_view, facades_total}`. В `evidence`: число лучей и лучей с водой, здания, закрывающие вид на этаже ниже `min_floor` (id, высота, источник высоты, расстояние), параметры расчёта и допущения.
- **Уверенность:** 0,85, если вид определяют здания с высотами кадастра (или помех нет); 0,6, если среди закрывающих есть высоты OSM; 0,45, если есть высота по умолчанию (15 м). Для фактов по фасадам: 1 016 / 94 / 75, по отелям: 203 / 1 / 4.
- **Результат на 25.10.2026:** фактов по фасадам 1 185 (море видно с 78 фасадов), по отелям 208. Вид на море есть у **20 отелей**: с 1–2 этажа у 13, с 3–4 у 2, с 5 и выше у 5. Из 22 береговых отелей (до 400 м) вид найден у 15, без вида 7: Gothic Cathedral Apartments, Hotel Ciutadella Barcelona, Hotel Hesperia Metropol, Hotel Oasis, Hotel Santa Marta, Park Hotel Barcelona, The Wittmore. Причины не разбирались, кроме Hotel Santa Marta: ближайшая вода по лучам его фасадов в 811 м при 328 м до береговой линии (береговой участок рядом, видимо, вне вееров его фасадов; не проверялось).
- **Выборочная проверка:** см. ниже, раздел про 5 известных отелей.
- **Допущения и ограничения:**
  - рельеф плоский (DEM не используется), деревья и надстройки не учитываются;
  - морем считается любая вода за береговой линией OSM, включая порты, марины и молы (Порт Вель, Порт Олимпик); отличить пляж от гавани алгоритм не умеет, допущение записано в `evidence.assumptions`;
  - этажность фасада считается по частям здания кадастра (`building_parts`): максимум по частям не дальше 15 м от фасадной линии, чей центр лежит за стеной; у зданий без частей — этажность здания. Фасады берутся по внешнему контуру, поэтому башня, отступающая от края подиума (Acta Voraport: башня в 49–77 м за стеной), вида через подиум не получает: стена башни в контуре не представлена. Решение на будущее — строить фасады по частям;
  - 762 фасада из 1 185 не нашли воду в радиусе 1,5 км по своему вееру.

**Найденный дефект и исправление.** Первая версия брала высоту здания кадастра по максимуму этажности его частей (`buildingpart.gml`) для всего контура: подиум башни (Hotel Arts) моделировался такой же высокой башней и закрывал вид собственным фасадам отеля (12 фасадов у 7 отелей, где ≥10 лучей доходят до воды, а главный блокирующий объект — само здание отеля). Исправление: `collect catastro` загружает части зданий с разной этажностью в `building_parts` (18 784 здания, 87 673 части), препятствия и этажность фасада считаются по частям. Результат: таких фасадов осталось 3 (у 3 отелей). Побочный эффект: Acta Voraport, Voraport Actahoteld, Hotel ILUNION Barcelona и башня Leonardo Royal потеряли вид, который показывала первая версия, потому что их башни стоят в глубине контура за низким подиумом (см. ограничения) — вероятно, ложные «нет». Таблица `building_parts` не входит в сид (9 МБ в сжатом виде): готовые факты и `evidence` в сиде есть, для пересчёта нужны сырые данные и `collect catastro` (около 5 минут).

## Кадастр Испании (Catastro, INSPIRE Buildings): загружен в БД

### Загрузка (этап 2)

- **Команда:** `cd backend && go run ./cmd/collect catastro`. Читает `data/raw/catastro/` (распакованные `*.building.gml` и `*.buildingpart.gml` либо zip рядом), потоковым разбором, в память целиком не грузит. Идемпотентна: здания обновляются по `catastro_ref`. Занимает около 12 секунд.
- **Что хранится:** отдельные строки в `buildings` (`osm_id` пустой, `catastro_ref` = кадастровая ссылка, `height_source = 'catastro'`, `levels` = максимум `numberOfFloorsAboveGround` по частям здания, `height_m` = этажи × 3 м). Контур берётся из `building.gml`, перепроецируется из EPSG:25831 в 4326 в PostGIS (`ST_Transform`). Здания OSM остаются отдельными строками как второй источник.
- **Отбор:** по габариту здания (`gml:Envelope`) против рамки районов охвата + 0,003°; здания без этажности пропускаются (у них остаётся высота OSM). Из 69 911 зданий муниципалитета в рамку попало 23 440, этажность есть у 23 392.
- **Части зданий:** если у здания этажность частей из `buildingpart.gml` различается (башня на подиуме), части сохраняются в `building_parts` (контур, этажи, высота = этажи × 3 м): 18 784 здания, 87 673 части из 23 392 зданий с этажностью. Нужны для препятствий и этажности фасада в `sea_view`. Загрузка двухпроходная (контуры зданий в рамке, затем части только этих зданий), команда занимает около 5 минут. В демо-сид таблица не входит (9 МБ в сжатом виде).
- **Привязка отелей** (`LinkHotels`, вызывается после `osm` и после `catastro`): `hotels.building_id` — здание кадастра, содержащее точку отеля, иначе ближайшее не дальше 15 м, иначе здание OSM; `hotels.osm_building_id` — здание OSM (way отеля или содержащее точку). Оба значения этажности хранятся без слияния.
- **Результат на 24.10.2026** (209 отелей): здание кадастра с этажностью у **209 (100%)**, здание OSM у 133 (64%). Там, где есть оба и у OSM известна высота, этажность расходится у 26 отелей (сравнение с округлением до этажа). Конфликты и факты пока не создаются, это задача этапа 3.
- **Данные, схема:** миграция `0004_catastro.sql` (уникальный индекс `catastro_ref`, колонка `hotels.osm_building_id`).
- **Ограничение:** у отеля, привязанного к зданию по запасному правилу «ближайшее ≤15 м», здание может оказаться соседним; доля таких отелей отдельно не считалась.

## Оценка шума по OSM (`noise_night_osm@1`, этап 3)

- Второй, независимый от карты BCN источник `noise_night`: дороги OSM (таблица `roads`, 300 м вокруг отелей) и ночные заведения (`pois`) в радиусе 150 м от середины фасада.
- Модель эвристическая: ночной уровень дороги по классу на расстоянии 10 м (trunk 70, primary 67, secondary 64, tertiary 60, residential и unclassified 55, living_street 46, pedestrian 38 дБ), затухание линейного источника 10·lg(d/10); клуб 62, бар и паб 52, biergarten 50 дБ, затухание точечного 20·lg(d/10); фон 33 дБ; уровни складываются по энергии. Источник вне ±75° от нормали фасада или закрытый чужим зданием на прямой видимости ослабляется на 20 дБ. Интенсивность движения и часы работы заведений не учитываются.
- Надёжность 0,6, группа независимости `osm_noise_estimate`.
- **Подстройка:** первый вариант (ослабление 12 дБ, уровни дорог на 4–7 дБ ниже, без проверки видимости) расходился с BCN на 60% фасадов. Я один раз подстроил ослабление и уровни малых дорог и добавил проверку прямой видимости; после этого согласны 68% (523 из 768 фасадов с картой), корреляция Ln 0,70, средняя разница OSM − BCN −2,6 дБ. Так как константы подстраивались под BCN, согласие слегка завышено; финальная калибровка и оценка — этап 8.
- **Конфликты:** расхождение источников на ступень и более (`conflict_threshold: 1`) создаёт запись в `conflicts` (245 открытых на 768 фасадов с картой); значение факта остаётся по BCN (0,85), оба свидетельства сохранены. Разрешает движок правды (этап 4). Там, где карта не покрывает фасад (417 фасадов, 3 демо-отеля без фасадного шума), факт строится по OSM с уверенностью 0,6.

## Пешеходный граф, метро и пляжи OpenStreetMap (этап 3)

- **Что и как:** Overpass API, `go run ./cmd/collect walk-data`, 26.10.2026, районы охвата с запасом 0,02° (~2 км); сырые ответы в `data/raw/overpass_walk_*.json` и `overpass_destinations_*.json`.
  - Пешеходный граф: `way[highway]` классов footway, pedestrian, path, steps, living_street, residential, service, unclassified, track, cycleway, tertiary, secondary, primary, trunk (и `_link`), без `foot=no` и `access=private|no`. Из 51 174 путей получено 111 312 рёбер между перекрёстками (`walk_edges`; в сид не входят, пересобираются командой).
  - Метро: `railway=subway_entrance` и `railway=station` + `station=subway` — 361 точка (`destinations`, вид `metro`).
  - Пляжи: городские пляжи Барселоны в OSM областями почти не размечены (`natural=beach` только у Соморрострo, остальное `natural=sand` — вольеры зоопарка, площадки). Поэтому целью считаются точки доступа: стенды правил пляжей AMB (`tourism=information` + `information=board`, имя «Platja …») и песок или пляж не дальше 120 м от береговой линии: 74 точки на 7 пляжах (Sant Sebastià, Sant Miquel, Barceloneta, Somorrostro, Bogatell, Nova Icària и безымянные участки песка). Mar Bella и пляжи дальше на северо-восток не попали. Это допущение: время до «пляжа» — до ближайшего стенда пляжа или кромки песка.
- **Лицензия:** ODbL, © участники OpenStreetMap.

## Пешие маршруты (`walk_route@1`, этап 3)

- `go run ./cmd/collect walk`: для каждого отеля кратчайший путь по графу (Дейкстра в Go, несколько стартов и целей) до ближайшего метро (предел 2,5 км) и пляжа (4 км). Точка отеля и цели привязываются к ближайшему ребру в радиусе 200 м (PostGIS, KNN по GiST): расстояние до ребра по прямой плюс вдоль ребра до узла. Скорость 80 м/мин (4,8 км/ч). Время округляется вверх до минуты.
- Факты `walk_to_beach` и `walk_to_metro` у отеля: минуты, метры, имя цели; в evidence — путь (до 150 точек для карты), привязка, параметры и допущения. Надёжность 0,7 (расчёт точный, но граф OSM неполон), группа `osm_walk_graph`, срок годности 180 дней.
- Не учитываются: рельеф, светофоры и переходы, реальный вход в отель (точка OSM). Старт и цель на одном ребре считаются через узел (небольшое завышение для отелей вплотную к цели).
- **Устаревшее зеркало (27.10).** Перезагрузка 26.10 в 13:30 попала на зеркало Overpass с базой OSM от 31.05.2026 (поле `osm3s.timestamp_osm_base`): песка 71 путь вместо 118, метро 354 вместо 361, пляжных точек после фильтра 65 вместо 74. Запрос и код не менялись. Минуты `walk_to_beach` на этих данных у 58 отелей сдвинулись на +1, у Hotel Barcelona Princess (330) 11 → 19, у Leonardo Royal Hotel (354) 12 → 18 (район Diagonal Mar). Клиент Overpass теперь отклоняет ответы со старше 7 дней базой и берёт следующее зеркало (`DefaultMaxDataAge`). После перезагрузки 27.10: 361 вход метро, 74 пляжные точки (490 точек границ до отсева не у берега), все 208 `walk_to_beach` и 207 из 208 `walk_to_metro` совпали с расчётом до сбоя, у одного отеля метро +1; у пяти береговых демо-отелей (Sofitel, Arts, Best Western 54, Barceló Antenea Mar, Occidental Atenea Mar) минуты 3, 4, 4, 5, 5 не менялись ни до, ни после. Число 322 в журнале — точки границ до фильтра при той же устаревшей выгрузке.
- **Результат:** маршрут найден у 208 из 209 отелей до пляжа и до метро. Медиана до метро 3–8 минут по районам, до пляжа: Барселонета 15, Готический 25, Эшампле 37 минут. Отношение длины пути к прямой — медиана 1,26, 5-й и 95-й процентили 1,07 и 1,49.

## Ночные сервисы (`night_services_osm@1`, этап 3)

- **Что:** что открыто ночью рядом с отелем — аптеки, магазины (supermarket, convenience), еда и напитки (бар, паб, клуб, кафе, ресторан, фастфуд) в радиусе 300 м по прямой от точки отеля. Источник — POI OSM (`collect pois`, таблица `pois`) и их тег `opening_hours`. Команда `go run ./cmd/collect night-services`.
- **Ночь:** 01:00 в среду (ночь будня) и в субботу (ночь выходных); хвост интервала предыдущего вечера считается открытым, заведение, закрывающееся ровно в 01:00, к этому моменту закрыто.
- **Разбор `opening_hours`:** собственный разборщик подмножества синтаксиса: `24/7`, дни и диапазоны (в т. ч. `Fr-Mo`), несколько интервалов, переход за полночь, `off`/`closed`/`open`, правила через `;` и группы дней через запятую, праздники (`PH`) игнорируются, позднее правило переопределяет раннее. Не поддерживаются `+`, восход/закат, месяцы и недели: такие часы считаются неизвестными.
- **Охват данных:** у 844 из 3 114 заведений (27%) в OSM есть `opening_hours`; из них разбирается 818 (96,9%); остальные 26 — «+» (открыто до неопределённого времени), месяцы, `13-02` без минут, опечатки. Заведения без часов открытыми не считаются (оценка осторожная: недооценка вероятнее переоценки); их число хранится в факте (`unknown_hours`).
- **Уровень:** `rich` — есть открытая ночью аптека или магазин и не меньше трёх открытых заведений еды и напитков; `basic` — есть аптека или магазин ночью, либо хотя бы одно открытое заведение; `none` — ничего. Результат: rich 81, basic 106, none 22 отеля; Готический и Эшампле в основном rich/basic, Diagonal Mar в основном none.
- В факте: по каждому виду всего, неизвестно, открыто в будни и в выходные и ближайшее открытое (имя, расстояние, часы); в evidence — до 15 открытых заведений с `osm_id`, допущения. Надёжность 0,6, группа `osm_pois`, срок годности 90 дней.
## Климат по месяцам: Open-Meteo (`climate_open_meteo@1`, этап 3)

- **Что и как:** `go run ./cmd/collect climate`, 26.10.2026. Для центра каждого из 6 районов запрашиваются суточные значения за последние 10 полных лет (2016–2025): Open-Meteo Historical Weather API (`https://archive-api.open-meteo.com/v1/archive`, реанализ ERA5: `temperature_2m_mean|max|min`, `precipitation_sum`, `sunshine_duration`) и Marine API (`https://marine-api.open-meteo.com/v1/marine`, `sea_surface_temperature`, почасовые значения усредняются по суткам, сутки с менее чем 12 часами данных пропускаются). Сырые ответы в `data/raw/openmeteo_*.json`. Ключ не нужен.
- **Лицензия:** CC BY 4.0, атрибуция Open-Meteo.com (нужна в README и UI). Бесплатный уровень предназначен для некоммерческого использования.
- **Расчёт:** по каждому месяцу: температуры воздуха (среднее по суткам; максимум и минимум — среднее суточных), осадки (среднее месячной суммы по годам, мм), дождливые дни (осадки не меньше 1 мм, среднее число за месяц), солнце (часы в сутки), температура воды (среднее по имеющимся суткам), признак «купание» (вода не холоднее 20 °C). Факт `climate_by_month` относится к сущности `district` (не к отелю): отель наследует климат района.
- **Результат:** надёжность 0,85, группа `open_meteo_era5`, срок годности 365 дней. Для Готического квартала: январь 8,8 °C, август 25,3 °C, годовые осадки 675 мм, максимум осадков в сентябре–октябре, вода подходит для купания в июне–октябре (в октябре 22,4 °C).
- **Ограничения:** ячейка реанализа 9–25 км, значения почти одинаковы для всех районов; температура моря есть не за все годы (в Marine API данные плотные только за последние годы: 4 года из 10), поэтому вода — оценка по доступным годам; ветер, волны и медузы не учитываются.

## Разметка для метрик качества (`data/labels/`, этап 8.2)

- **Что:** метки по 18 демо-отелям (вид на море, тихие номера ночью, шумная улица) для проверки `sea_view` и `noise_night`; файл `data/labels/sea_view_noise_night.yaml`.
- **Откуда:** публичные страницы отелей и агрегаторов (Booking, Tripadvisor, Expedia, Hotels.com, barcelona.com, официальные сайты и обзоры), найденные веб-поиском. У каждой метки — ссылка, короткое примечание и уверенность разметчика (`sure` / `likely` / `unknown`). Страницы целиком не открывались, использовались сводки поиска.
- **Запросы и дата:** по одному-двум запросам на отель вида «<название> Barcelona sea view rooms noise», 28.10.2026. Результаты поиска не воспроизводимы дословно: страницы и сводки меняются.
- **Лицензия:** в репозиторий попадают только ссылки и наши формулировки, текст источников не копируется. Метки — оценка разработчика, а не данные источников.
- **Ограничения:** не натурный эталон, часть источников маркетинговая; подробности и выводы — `docs/metrics.md`. Обновление: правка YAML и `collect metrics` (команда только читает БД).
