## Правила работы

- Бэкенд — Go в `backend/` (там go.mod), фронтенд — React + Vite в `frontend/`. Стек, БД и структура — раздел 8 PROJECT_CONTEXT.md.
- Бэкенд и фронтенд общаются только через JSON API под `/api`. Фронтенд не знает о БД, бэкенд не генерирует HTML.

## Архитектура

Подробности и раскладка по папкам — раздел 8 PROJECT_CONTEXT.md. Нарушать эти правила нельзя; если правило мешает, остановись и предложи изменение, а не обходи его.

Backend — Clean Architecture, прагматично:

- Зависимости только внутрь: `adapter` → `usecase` → `domain`. `domain` не импортирует БД, HTTP, LLM и внешние клиенты.
- Порты (интерфейсы) объявляются в `usecase` у потребителя, реализуются в `adapter`. Интерфейсы — только на внешних границах (БД, источники данных, LLM), без абстракций «на всякий случай».
- SQL и PostGIS — только в `adapter/repository/postgres`. Бизнес-логика расчётов — в `usecase`/`domain` и тестируется без БД.
- `cmd/*` только запускают приложение; сборка зависимостей — в `internal/app`.
- DTO HTTP отделены от сущностей домена.

Frontend — Feature-Sliced Design:

- Слои: `app` → `pages` → `widgets` → `features` → `entities` → `shared`. Импорт только вниз; слайсы одного слоя не импортируют друг друга.
- Импорт слайса извне — только через его `index.ts`.
- Запросы к API — в `shared/api` (базовый клиент) и сегментах `api` слайсов. Компоненты не вызывают `fetch` напрямую.
- Новое не класть в `shared`, если оно знает о предметной области — это `entities` или `features`.
- Технические правила организаторов (раздел 2.1) обязательны: `docker compose up --build` без доп. шагов, порт 8080, `/health`, non-root, multi-stage, зафиксированные версии. Не нарушай их ни на одном этапе.
- Без `LLM_API_KEY` приложение должно работать в режиме кеша.
- Работаем по этапам из раздела 9 PROJECT_CONTEXT.md. В начале сессии уточни номер этапа и его критерий готовности. Задачи других этапов не делай.
- Перед кодом коротко предложи план и согласуй его. Без больших рефакторингов «на будущее».
- LLM никогда не является источником факта. Каждый факт пишется в `facts` с source, method, confidence, observed_at, valid_until, evidence.
- Тесты — на расчётную логику (geo, конфликты, разбор ответов). UI и обвязку тестами не покрываем: время важнее.
- БД — Postgres 16 + PostGIS. Пространственные выборки делай в SQL с GiST-индексами, логику поверх них — в Go. Схема меняется только миграциями в `migrations/`.
- Сырые выгрузки — в `data/raw/` в корне (gitignore). В git только `data/demo/` (seed.sql.gz) размером до нескольких МБ.
- Секреты только в `.env`. Пример держим в `.env.example`: `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`.
- Каждую выгрузку данных документируй в `docs/data.md`: откуда, какой запрос, когда, лицензия. Этого требуют организаторы.
- В конце этапа обнови раздел «Статус и решения» в docs/PROJECT_CONTEXT.md и предложи сообщение коммита.

## Git, коммиты и пул-реквесты

- Никогда не коммить и не пушь в `main`. Одна задача — одна ветка `<тип>/stage<N>-<кратко>`, например `feat/stage1-docker-skeleton`.
- Коммиты — по Conventional Commits: `<тип>(<область>): <описание>`.
  - Типы: `feat` — новая функциональность; `fix` — исправление ошибки; `refactor` — изменение кода без изменения поведения; `perf` — производительность; `test` — тесты; `docs` — документация; `build` — Docker, зависимости, сборка; `ci` — CI; `chore` — прочее обслуживание (конфиги, .gitignore, форматирование).
  - Области: `backend`, `frontend`, `db`, `data`, `geo`, `search`, `hotelier`, `registry`, `llm`, `docker`, `docs`.
  - Тип и область — на английском, описание — на русском, в повелительном наклонении, без точки, до 72 символов. Пример: `feat(geo): добавить расчёт вида на море по этажам`.
  - Ломающее изменение схемы или API — `!` после области и строка `BREAKING CHANGE:` в теле.
  - Один коммит — одно логическое изменение. Не смешивать рефакторинг и новую функциональность в одном коммите.
- Перед пушем обязательно: `go test ./...` и `go vet ./...` в `backend/`, `gofmt -l .` в `backend/` (вывод должен быть пустым), `npm run build` в `frontend/`, если он менялся; если менялись Docker, миграции или сиды — `docker compose up --build` и проверка `/health`.
- Проверка «с нуля» (чистая БД, загрузка сида, воспроизведение кеша) — только в отдельном проекте Compose: `docker compose -p clean-check up --build`, затем `docker compose -p clean-check down -v`. Рабочий том проекта по умолчанию `down -v` не удалять: в нём таблицы, которых нет в сиде (`walk_edges`, `destinations`, `building_parts`). Рабочий стек на время проверки (порт 8080) останавливать через `docker compose stop`, потом поднимать `docker compose start`. Режим жюри без ключа LLM проверяй так: `docker compose -p clean-check -f docker-compose.yml -f docker-compose.nollm.yml up --build` (`docker-compose.nollm.yml` задаёт пустой `LLM_API_KEY`).
- Демо-сид (`data/demo/seed.sql.gz`) пересобирай и коммить только в последней задаче этапа, одним коммитом `build(data): пересобрать демо-сид`. В промежуточных задачах проверяй сид локально, но не коммить: каждая версия бинарного файла навсегда остаётся в истории git.
- PR создавай через `gh pr create` в `main`. **Заголовок и описание PR — на русском.** Заголовок в формате Conventional Commits. Описание по шаблону:

  ```
  ## Что сделано
  ## Зачем
  ## Как проверено
  (команды и их результат)
  ## Изменения в схеме, данных или API
  ## Что не сделано или под вопросом
  ```

- Не используй `git push --force` и не переписывай историю `main`.
- Не читай целиком большие файлы из `data/raw/`: смотри структуру через `head`, `jq` или короткий Go-скрипт, чтобы не тратить контекст.

## Команды

- Сбор и расчёт: `cd backend && go run ./cmd/collect <команда>`
- Расчёт по одному отелю и с параметрами: `go run ./cmd/collect sea-view -hotel 12 -param fan_half_deg=30`; регион — `-region <код>` (по умолчанию `barcelona`); описания инструментов и параметры — `go run ./cmd/collect tools`
- Новая характеристика текстом: `go run ./cmd/collect add-characteristic "<описание>"` (без `LLM_API_KEY` — заготовки из кеша)
- Агент-сборщик по отелю: `go run ./cmd/collect agent -hotel 161` (ключ задан — LLM с записью в кеш; нет ключа или `-cache` — из кеша; `-planner` — без LLM); проверка ключа: `go run ./cmd/collect llm-check`; журнал — `GET /api/hotels/{id}/trace`
- Категории номеров: `go run ./cmd/collect mock-rooms [-hotel ID]` (мок категорий и размещения демо-отелей, «Sea View»), затем `go run ./cmd/collect rooms [-hotel ID]` (значения характеристик в категориях); описание — `docs/rooms.md`, API — `GET /api/hotels/{id}/rooms`
- Сервер: `cd backend && go run ./cmd/server`
- Фронтенд: `cd frontend && npm run dev`
- Тесты: `cd backend && go test ./...`
- Полный запуск (из корня): `docker compose up --build`
